## 二、三条不可动摇的约束

来自 `CLAUDE.md`,违反了就是方向性错误:

1. **零二进制资产。** 仓库里只能有文本文件。贴图运行时程序化生成到 `DataTexture`,
   音效用 Web Audio 合成。**写实和零资产不冲突** —— 沥青、沙地、混凝土护墙、
   法线贴图全是运行时算出来的。
2. **改完必须自己看画面。** 跑 `npm run shoot`,然后用 Read 工具**真的打开那张 PNG**。
   编译通过 ≠ 画面正确。见第五节,这个项目在这上面栽过很多次。
3. **一个里程碑一个 PR。** 不要顺手做下一个里程碑的事。

### 视觉方向(2026-08 由人类改定)

原定的「低多边形」**已作废**,改为尽量接近实拍照片。天花板写在 `CLAUDE.md`:

- **能做到接近实拍**:光照、大气散射、PBR 材质、色调映射、后处理。
- **做不到实拍级**:复杂**造型**。手写 `BufferGeometry` 出不了照片级的载具外形。
  人类已经指出过「车子太假」,并且明确这不是当前阶段的事 —— **材质可以继续救,
  造型不要硬碰**。

## 三、代码地图

```
src/core/     引擎无关:定步长主循环、seeded PRNG、输入层、数学工具、测试接口
src/game/     玩法:载具物理、赛道生成与查询、相机、计时、数值
src/gfx/      渲染:大气、贴图生成、各种网格、后处理链、配色
scripts/      截图与性能脚手架
tests/unit/   逻辑测试(180 条)
tests/visual/ Playwright 截图冒烟(13 条)
```

### 几个关键文件

- **`src/game/tuning.ts`** — 所有手感与视觉数值的唯一来源,分 `VEHICLE` / `CAMERA` /
  `TRACK` / `SKY` / `CRAFT` / `POST` 六段。**人类调手感只改这一个文件。**
  每个值都写了「为什么是这个数」,好几处还写了「改这个必须回头核哪个」。
- **`src/game/course.ts`** — 赛道的两段式地面查询。**全项目最重要的不变量所在。**
- **`src/game/vehicle.ts`** — 悬浮控制器。物理都在这儿,数值都不在这儿。
- **`src/gfx/postprocess.ts`** — 后处理链。顺序有硬约束,注释里写了为什么。
- **`src/gfx/atmosphere.ts`** — 大气与 IBL。里面有一道**必须存在**的辐射钳制。
- **`src/gfx/textures.ts`** — 程序化 PBR 贴图生成器。

## 四、必须理解的不变量

破坏它们不会立刻报错,但会让整个项目慢慢烂掉。

### 1. 物理查询的面 == 渲染出来的面

`Course` 预先算好一张条带顶点网格,**渲染网格和 `sample()` 吃同一张表、同一套
三角划分**。`tests/unit/course.test.ts` 拿 600 个三角形重心直接断言这一点。

**推论:同一条边只能有一个高度。** 护墙也必须坐在条带自己的外缘顶点上
(`Course.buildEdgeLine()`)。老版护栏照着 `sample.y` 和 `bank` 另算了一套高度、
还带一个 0.5 的经验系数,结果墙底和路肩对不上,远看就是一条浮在地上的带子。

赛道外的地形是例外(噪声高度 + 有限差分法线),那里是出界区。

### 2. 同一个 seed 必须逐帧复现

- `src/` 下**禁止 `Math.random()`**,`tests/unit/noMathRandom.test.ts` 会扫描拦截。
- 所有随机走注入的 `Rng`(mulberry32),用 `fork()` 派生子流。
- 主循环是定步长累加器,`?test=1` 时**完全不注册 rAF**,只由 `advance(n)` 推进。
- `InputRecorder.record()` 会**就地**把实时输入量化成回放精度。

### 3. 截图回路是这个项目的地基

CI 没有 GPU,WebGL 走 SwiftShader。`npm run shoot` + `tests/visual/smoke.spec.ts`
是 agent **唯一能看见画面**的途径。

**性能预算(实测,1280×720,chase 机位):**

| 配置 | 每帧 |
|---|---|
| 无后处理 | 325 ms |
| 仅 composer(RenderPass + OutputPass) | 347 ms |
| 默认链(bloom + SMAA + 暗角) | 621 ms |

冒烟测试全套 **2~2.5 分钟**(M0 时是 27.7 秒)。**这条回路挂了就等于瞎着写代码,
变得太慢要先停下来解决,不要硬推。**

### 想提速的话,先看这份实测(免得往错的方向使劲)

一次 `driveScene`(goto → ready → 首帧 → advance(120) → 截图)的分解,热态:

| 阶段 | 耗时 |
|---|---|
| JS 加载解析 | ~1.5 s |
| `World` 构造(赛道 + 地形 + 护墙网格) | ~2.1 s |
| 程序化贴图 ×3 | 0.15 s |
| **PMREM 烘焙** | **0.08 s** |
| **首帧渲染(含 shader 编译)** | **~7.4 s** |
| 之后每帧 | 0.62 s |

**三个反直觉的点:**

1. **PMREM 和贴图生成都不是瓶颈**,加起来不到 0.25 秒 —— 别去优化它们。
2. **首帧的 shader 编译才是大头**,但**减少 `goto` 次数省不到这笔钱**:同一个
   `page` 对象的多次 goto 之间,浏览器会复用编译好的 shader。这条路试过了,
   收益在噪声里(把某条测试的 goto 从 6 次减到 3 次,全套时间没有可测的变化)。
3. **冷启动占比很高**:同一段代码第一次跑 12.9 秒,第二次 3.7 秒。CI 每次都是冷的,
   所以本地测出来的时间会系统性偏乐观。

真要提速,剩下的方向是降低渲染分辨率(会动所有截图基准)或砍后处理级数
(会让 agent 看不到真实画面)—— 两个都有代价,**动之前先想清楚代价谁来付**。

## 五、这个项目吃过的亏

按「只有看图才能发现」的程度排序。前四条是历史,**第 5、6 条是 M3 这轮的,
而且是同一类**。

1. **转向左右反了。** 单测断言的是「yaw 与 steer 同号」,而 yaw 正方向到底是左是右
   *正是搞反的那件事* —— 断言和 bug 共用同一个错误前提,83 条测试全绿也拦不住。
   **教训:断言物理位置,不要断言内部约定的符号。**
2. **烘环境贴图时天空整个变黑。** `scene.add(sky)` 会把天空从世界场景摘走。
3. **地形三角形压在赛道上。** 剔除只按重心判断。
4. **贴地阴影不出现。** 扇形三角的绕序反了,整个面朝下被背面剔除。
   护墙现在按左右侧分绕序,`tests/unit/trackMesh.test.ts` 拿三角形**自己的叉乘**
   和着色法线做断言 —— 那条测试验证过:故意改回同一套绕序,它报 -0.9999。
5. **车漆反射成磨砂玻璃。** metalness 高了之后基色只决定反射色调,车身没有自己的
   颜色。**同一个坑踩了两次**:第一次修了 hull,漏了 fin,直到人类看图才发现
   侧翼是块比尾焰还亮的白斑。

### 6. 两次 NaN 黑屏 —— 这一类最难认,务必读完

两次都是 **HDR 值溢出成 Inf/NaN,再被某个模糊/卷积核摊到一大片**:

- **bloom**:天空冲破 `HalfFloatType` 的 65504,高通之后被 mip 链一摊,整屏变黑。
- **天空辐射污染 IBL**:Preetham 在太阳附近能算到上千(shader 里 `EE = 1000`),
  烘 PMREM 时溢出,**整张环境贴图变 NaN,所有 PBR 材质一起变黑**。表现是
  「天空正常、地面纯黑剪影」,看着像地形没被照亮。太阳仰角一过 15 度就触发。

两处钳制现在分别在 `gfx/postprocess.ts` 的 `clampBloomInput()` 和
`gfx/atmosphere.ts` 的 `clampSkyRadiance()`,**都不能删**。

**NaN 有传染性,这是它难认的根源**:把 `bloomStrength` 或 `environmentIntensity`
调成 0 也照样黑,因为 `0 * NaN` 还是 NaN。所以「关掉某个效果看看」这个惯用的
排查手段在这里会给出错误结论。

**而它们差点漏过去的原因,比 bug 本身更值得记住:**

- **`npm run shoot` 的默认 seed 是 42,而 42 恰好是两个 bug 都幸免的少数 seed 之一。**
  所有回归截图都是好的,只有实时模式(默认 seed 1337)是黑的。
  **换 seed 复核,不要只信默认那一张。**
- **既有的冒烟断言结构性地拦不住这类问题。** 「换 seed 会换掉地形与配色」断言的是
  两个 seed 之间平均色差够大 —— 而一张正常图和一张全黑图之间的色差**更大**,
  断言反而更容易通过。方差同理:天空正常而地面归零时,画面对比度更高、方差更大。
  现在补了 `lowerMeanLuminance`(画面下半幅平均亮度),逐个 seed、两头都卡。

### 7. 默认 seed 42 第三次让问题溜过去

「出生点落在逆光位置」这条是人类试玩提的,而**任何一张默认截图都拍不到它**:

| seed | 出生时车头与太阳的夹角 |
|---|---|
| **42**(`npm run shoot` 默认) | **161°** —— 太阳在正后方,完全没问题 |
| **1337**(线上实际默认) | **12.5°** —— 几乎直视太阳 |

和两次 NaN 黑屏是同一个结构:**42 恰好是好的那个**。这已经是第三次了,
所以现在 `World.sunAhead` 把「车头有多正对太阳」暴露成可断言的量,
`tests/unit/trackLayout.test.ts` 拿 12 个 seed × 12 个方位角扫它 ——
不再依赖某个人恰好换了 seed 去看一眼。

### 两个测量方法的坑

- **别拿速度差反推侧向加速度。** 车头转动本身会让机体系下的侧向速度以 ω·v 变化。
  `Vehicle.lateralGripAccel` 直接暴露抓地力实际施加的加速度。
- **测试失败时先找真实原因,别急着放宽容差。** 左右镜像那条差了 0.04°,看着像浮点
  噪声,实际是出生点压平区不够长。放宽容差会把真实原因永久盖掉。
  M3 这轮又遇到一次:空中回正那条从「侧滑角绝对变化 < 5°」改成了「侧滑角**没有向
  0 收敛**」—— 后者才是回正力矩真正的特征,前者的容差会跟着手感数值一起漂。

## 六、当前手感数值(实测)

改 `tuning.ts` 之后这些会变,`tests/unit/vehicle.test.ts` 和 `grip.test.ts` 里的
区间就是它们的规格书 —— **测试挂了不一定是 bug,但一定意味着手感变了,需要人类确认。**

| 项目 | 值 |
|---|---|
| 0 → 100 km/h | **2.3 s**(人类反馈 0.92 s「太快、不写实」后放慢) |
| 极速 | 315 km/h |
| 峰值侧向抓地加速度 | 3.80 g |
| 满舵侧滑角峰值 | 57°(甩尾,不是打转) |
| 赛道长度 | 2.8–3.4 km,10 个 seed 全部可跑完 |

**两条关键设计:**

- **偏航角速度上限由可用侧向力推出(ω = a_lat / v),外加侧滑回正力矩。**
  少了任何一个,车都会一打方向就原地打转。
- **恒定推力下,起步加速度和极速是绑死的。** `a(0) = thrust`,极速由推力与阻力的
  平衡点决定。所以放慢起步必须同步降阻力,否则极速一起掉(实测 thrust 34 → 13
  会让极速掉到 154 km/h)。降的是**线性项**(0.18 → 0.05)—— 那是轮胎滚阻的量级,
  而这台车没有轮胎。代价是松油门滑行更久,那反而更贴合设定。

## 七、后处理链的取舍(有数据支撑,别凭感觉改)

`RenderPass → bloom → OutputPass → SMAA → 暗角`。顺序有硬约束,排错了不报错、
只让画面悄悄变糟 —— 理由写在 `postprocess.ts` 的类注释里。

**AO 实现了但默认不启用**,这是量出来的决定:

| 环节 | 每帧成本 | 画面差异 |
|---|---|---|
| 暗角 | +45 ms | 明显 |
| bloom | +155 ms | 明显 |
| SMAA | +178 ms | 明显 |
| **AO** | +169 ms | **平均 3.8/255,肉眼看不出** |

AO 弱不是配置错了:开阔沙漠、平坦赛道,**而且反重力载具悬浮在地面 1.6 米以上,
连接触点都没有**。半径从 0.45 米加到 2.5 米差异反而更小。M5 的隧道段进来之后,
把 `'ao'` 加回 `DEFAULT_STAGES` 即可。

### bloom 阈值:一个数不能同时服务两个目标

阈值既要**压住整片天空**(否则逆光时全屏发白),又要**放行尾焰**(否则速度感没了)。
上一版为了救逆光把它从 3.5 提到 8,却没同步抬尾焰亮度 —— 尾焰当时是 6.2,正好掉到
阈值以下,辉光整个消失,**是人类试玩才发现的**。

现在两边分开:阈值留在 8 压天空,尾焰亮度(`CRAFT.thrusterFullGain`)抬到约 15。
两处注释互相点名。**改任何一边都要回头核另一边。**

## 八、工作方式

- **分支**:harness 每轮指定固定分支。**PR 合并后必须从 `origin/main` 重开同名分支**,
  不能往已合并的历史上继续堆提交。
- **提交前必过**:`npm run typecheck` / `npm run test -- --run` / `npm run build` /
  `npm run test:visual`。
- **人类的反馈风格**:给的是现象(「车太飘」「视角偏得离谱」「眼睛要瞎掉」),
  需要自己去测量、定位根因。他会验收手感和画面,**这两件事不要自己下结论**。
- **额度有限**,他会喊停。停的时候确保工作已提交推送。

### 常用命令

```bash
npm run dev                                     # 本地开发
npm run shoot                                   # 截图(默认 chase 机位、seed 42)
npm run shoot -- --camera=side --throttle=0     # 静止侧视,看载具本身
npm run shoot -- --seed=99 --frames=420         # 换 seed / 跑到赛道深处
npm run shoot -- --extra=post=none              # 关掉后处理做对比
npm run shoot -- --no-build                     # 复用现有 dist,连拍时省时间
npm run perf                                    # 量每帧渲染成本
```

机位:`chase` / `side` / `front` / `top` / `map`。
`?course=flat` 切回 M1 那块平地,`?post=none` 关掉整条后处理链。

**`npm run perf` 为什么必须存在**:`shoot` 和冒烟测试的墙钟时间**量不出**每帧成本 ——
`Loop.advance(n)` 走 n 个物理步之后只渲染一帧,那两个数字里绝大部分是构建、
启动和场景生成。perf 改成逐帧 `advance(1)`,再用一次截图强制结算 GL 队列。
(顺带一提:页面内的 `performance.now()` 也量不准,它只看到命令提交的时间 ——
实测 0.4 ms/帧,而墙钟是 325 ms/帧。)

## 九、方向转变:反重力 → 真实车辆

**人类已定:载具从「反重力悬浮」改成「真实车辆比赛」。优先级高于 `PLAN.md` 里
剩下的里程碑。**

### 要推翻的

- **`src/game/vehicle.ts` 的整个物理模型。** 现在是单点 raycast 悬浮 + 速度积分,
  没有轮胎、没有悬挂行程、没有档位。
- **`tuning.ts` 的 `VEHICLE` 段几乎全部作废**(thrust、悬浮刚度、偏航包络那些),
  `CRAFT` 段的尾焰也失去意义。
- **`src/gfx/craft.ts` 的载具几何** —— 现在是个没有轮子的悬浮体。人类已经说过
  「车子太假」,新方向下要重做,而且要有轮子。
- **`CLAUDE.md` 里「不用物理引擎、自写 raycast 悬浮」那条技术选型**要重新表述
  (是否引入引擎见下一节的分析)。

### 可以原样留下的(别推倒重来)

- **赛道生成与地面查询**(`trackLayout` / `course` / `spline`)。
  「物理查询的面 == 渲染出来的面」这个不变量对真实车辆**更重要** ——
  四个轮子要各自采样,精度问题会被放大四倍。
- 整条渲染管线:大气、IBL、PBR 贴图、后处理链、护墙。
- 截图验证回路、seeded PRNG、定步长主循环、输入录制。
- `tests/unit` 里除 `vehicle` / `grip` 之外的全部测试。

### 三处「为悬浮而写」但换成真车依然需要的东西

换模型时容易连着一起删掉,那会把踩过的坑重新踩一遍:

1. **偏航角速度上限由可用侧向力推出**(ω = a_lat / v)。真实车辆同样需要,
   否则一打方向就原地打转。
2. **静止时转向权限衰减到 0**。真车也一样,不然是坦克。
3. **悬浮间隙 1.6 米这个前提没了之后,AO 会重新变得有意义**(见第七节 ——
   现在 AO 是默认关的,理由正是「载具悬浮着、没有接触点」)。

## 十、物理引擎:**人类已拍板「加入」**(2026-08-21)

> **决定:引入物理引擎。** 下面这套「建议不引入」的分析是拍板**之前**写的,
> 保留原文是因为它列清了代价 —— 那几条代价现在变成了必须处理的事项,
> 见本节末尾的〈拍板之后要做的事〉。**不要再拿它去反驳已经定下的方向。**

**(以下为原分析)结论先说:建议不引入,把单点悬浮扩展成四轮 raycast。** 理由如下,拍板时可以推翻,
但请先读完再推翻。

### 引擎给什么、不给什么

- **给的**:刚体积分、碰撞检测、约束求解、翻滚姿态。
- **不给的**:**轮胎模型** —— 而赛车手感的绝大部分就在轮胎上。Rapier 没有内置车辆;
  Ammo/Bullet 有 `btRaycastVehicle`,但轮胎是个简化摩擦圆,要写实还是得实现
  Pacejka 之类的公式。

**所以最难的那部分,用不用引擎都要在本项目里实现。** 而引擎能替我们省掉的
(刚体积分 + 地面查询),恰好是这个项目**唯一不缺**的东西。

### 三处具体冲突

1. **确定性 —— 风险最大。** 第四节的不变量 2「同一个 seed 必须逐帧复现」是整个
   测试体系、`?test=1` 步进、以及 M4 幽灵回放的地基。物理引擎的求解器是迭代的、
   对浮点累加顺序敏感;Rapier 声称同平台确定性,跨平台(开发机 vs CI runner)
   不保证。现在这套自写积分是逐位可复现的,而且有测试盯着。
2. **WASM 撞上「零二进制资产」。** Rapier / Jolt 都是编译成 `.wasm` 的,会进 `dist/`。
   `CLAUDE.md` 第一条写的是「仓库里应该只有文本文件」—— 要不要为它破例得人类拍板。
   纯 JS 的 `cannon-es` 不违反这条,但质量与确定性都更差。
3. **包体积。** Rapier3d 的 WASM 一兆起步,当前整个产物才 691 KB,而 M6 是移动端与性能。

### 建议的替代做法:四轮 raycast

`Course.sample()` 已经支持任意点的精确查询,所以把**单点**悬浮扩展成**四个轮子
各自 raycast** 是顺理成章的:

- 每个轮子:悬挂力(弹簧 + 阻尼)+ 轮胎力(纵向驱动/制动、横向侧偏)
- 四个点的力自然产生 **pitch / roll 力矩** → **载荷转移是免费的**,
  刹车点头、过弯侧倾都直接出来
- 车身做刚体积分

**这是绝大多数赛车游戏的实际做法(raycast vehicle),不是妥协方案。**
它保住了确定性、零资产,以及现有的全部测试基础设施。

引擎真正不可替代的场景是**车与车碰撞、翻滚堆叠** —— 而 `CLAUDE.md` 明确
「不做联机 / 多人」,这个需求不存在。

### 如果人类决定还是要用引擎

选 **Rapier**(three 生态最主流、维护最好、确定性最强),并且明确接受三件事:

1. 在 `CLAUDE.md` 里为 WASM 破例,写清楚理由
2. **放弃跨平台逐帧复现**,M4 的幽灵回放改成存**位置轨迹**而不是存输入重放
3. 首屏体积涨 1MB+,留到 M6 处理

### 拍板之后实测:上面那条「确定性风险最大」是**错的**

原分析把「确定性」列为最大风险(第 1 条),理由是求解器迭代、对浮点累加顺序敏感。
**接上之后量了一遍,这条对 WASM 编译的引擎不成立。**

WebAssembly 的浮点语义由规范强制(IEEE-754,不允许 FMA 合并、不允许重结合、
没有扩展精度),所以同一份 wasm 在任何符合规范的运行时上结果必然一致 ——
这恰恰是**原生**编译的物理引擎做不到的事。原分析拿的是原生物理引擎的常识,
套到 wasm 上就不对了。

实测:接触密集的场景(倾斜地面 + 持续偏心力 + 一路滑移翻滚)跑 600 步,
**Node 和 Chromium 的 10 个状态字段逐位完全相同**。
守卫在 `tests/unit/physics.test.ts`,并钉了一组基准值。

于是原分析里那两条连带的让步也不需要了:

- 车辆物理单测**继续留在 vitest**(8 秒),不用搬进 Playwright(2 分钟)。
- M4 幽灵回放**可以继续存输入序列**重放,不必退化成存位置轨迹。

**基准值那条测试哪天红了,不要放宽它。** 它红只有一个含义:求解器动过了
(多半是升级了 Rapier),所有手感数值和回放基准都要重新核,需要人类确认。

### 为什么用 compat 版(体积更大却选了它)

| 包 | JS(gzip) | wasm(gzip) | 合计 |
|---|---|---|---|
| 无引擎(改之前) | 202 KB | — | **202 KB** |
| `rapier3d`(独立 .wasm) | 235 KB | 762 KB | **997 KB** |
| `rapier3d-compat`(base64 内联) | 1285 KB | — | **1285 KB** |

独立 wasm 版小 288 KB,但**它在 vitest(Node)里根本 import 不起来**:那个包
是给打包器用的,`package.json` 没有 `main`/`exports` 入口;加 alias 绕过之后,
wasm-bindgen 的堆表又会在 Vite 的 Node 变换下失配(`getObject` 返回 undefined)。

而「浏览器用一个包、测试用另一个包」是不能接受的 —— 这个项目整套测试的前提
就是**单测能预测运行时行为**,两个不同的构建产物会把这个前提悄悄挖空,
而且是那种「测试全绿但线上是坏的」的挖法,这个项目已经栽过两次。
**用 288 KB 换「测的和跑的是同一个二进制」。**

### 任务 B:原地打转的诊断结论(详见 `docs/tasks/spin-diagnosis.md`)

一句话:**车打转的根因是「后轮持续空转(滑移率 15~80 vs 设计峰值 0.12),
摩擦圆被纵向吃光,后轴侧向抓地几乎归零(只剩前轮的 3~15%)」,叠加
「左右后轮载荷不对称 → 纵向驱动力产生净偏航力矩」,一旦有了初始偏航就

### 二、任务 1: 拆除车身人工回正力偶, 实现纯轮胎级 SAT

#### 1. 为什么原先的做法必须返工?
在 `5ac5885` 中, 为了迅速抑制打转, 在 `Vehicle.update()` 末尾加入了:
```ts
const Iz = (CAR.mass * (CAR.bodyWidth ** 2 + CAR.bodyLength ** 2)) / 12;
const beta = Math.atan2(vLeft, vLong);
const restoreTorque = Iz * (k * beta - c * this.yawRate);
const coupleForce = restoreTorque / CAR.wheelBase;
// 在车头与车尾质心前后直接打纯横向力偶:
this.physics.addForceAtPoint(body, chassisLeft * coupleForce, ..., front);
this.physics.addForceAtPoint(body, -chassisLeft * coupleForce, ..., rear);
```
这是直接往车身刚体上加挂的人工弹簧阻尼器, 绕过了轮胎力与接触面物理, 属于违背项目宪法的手感补丁。

#### 2. 纯轮胎级 SAT 的物理模型推导与实现
根据现代汽车动力学 (Pacejka's Magic Formula & Caster Trail Geometry):
轮胎侧偏时, 接地印痕的侧向合力作用点位于接触中心后方, 形成自回正力矩 (Self-Aligning Torque, SAT):
1. **主销后倾机械拖距 ($t_{\text{caster}}$)**: 由转向主销后倾角（caster angle ≈ 5°~8°）在地面投影形成的几何杠杆臂（$t_{\text{caster}} \approx 0.16\text{ m}$）。无论侧偏角多大, 机械拖距始终恒定存在, 保证大侧滑角/极限漂移时依然保有强劲的物理回正力矩。
2. **气胎拖距 ($t_{\text{pneumatic}}$)**: 由轮胎接地印痕弹性变形引起的压力中心后移。在小侧偏角纯弹性区最大 ($t_{\text{pneumatic}} \approx 0.10\text{ m}$), 随着侧偏角增大轮胎进入完全滑动区, 气胎拖距平滑衰减至 0:
   $$u = \frac{|\alpha_i|}{\alpha_{\text{peak}}}$$
   $$t_p(\alpha_i) = t_{\text{pneumatic}} \cdot \frac{\max(0, 1 - u)}{1 + u^2}$$
3. **轮胎自回正力矩**:
   $$\text{SAT}_i = - (t_{\text{caster}} + t_p(\alpha_i)) \cdot F_{y,i}$$
4. **接地印痕偏航剪切阻尼**:
   轮胎接地胶块在地面旋转时存在微观剪切阻尼力矩, 随垂直载荷成正比缩放, 为整车提供轮胎级的偏航振荡抑制, 消除无阻尼摆头 (tank slapper):
   $$\tau_{\text{damp}, i} = - D_{\text{align}} \cdot \omega_y \cdot \frac{F_{z,i}}{F_{z0}}$$
5. **力矩施加**:
   在 `Vehicle.update()` 的四轮循环中, 计算每个轮子的 $\text{SAT}_i + \tau_{\text{damp}, i}$, 沿地面法向量通过 `Physics.addTorque(body, \mathbf{n} \cdot (\text{SAT}_i + \tau_{\text{damp}, i}))` 作用在刚体上。

#### 3. 动力学参数收敛 (`src/game/tuning.ts`)
所有新参数全部收敛在 `src/game/tuning.ts` 中:

#### 1. 1.5 秒起步加速与位移阈值运动学推导

### 四、任务 3: `src/game/autopilot.ts` 的逻辑定位与必要性论证

#### 1. Autopilot 的本质属性
`Autopilot` 是本项目用于持续集成自动化验收「10 个 seed 随机赛道均能零出界跑完一整圈」的 **Harness 验收工具**, 并非给玩家开车的辅助外挂。

#### 2. 为什么物理修好后依然需要合理的自动驾驶曲率预判?
1. **物理限制的真实性**: 在纯物理轮胎摩擦圆模型下, 车辆拥有真实的极限侧向附着能力 (1.3~1.6g)。当车速高达 250~300 km/h 时, 任何弯道半径 $R < \frac{v^2}{1.5g} \approx 300\text{ m}$ 的急弯, 在物理定律上都**不可能全油门不减速通过** (否则必触发 $F_y > \mu F_z$ 突破摩擦圆滑出赛道撞墙, 正如 `grip.test.ts` 专门验证的那样)。
2. **纯追踪算法的前视决策**: Autopilot 必须模拟专业车手的基本驾驶行为 —— 入弯前提前观察前方道路切线偏转角与坡度 (`dTangent > 0.10 || bend > 0.05`), 在入弯前合理减速退入物理可承受的安全车速窗口, 出弯后再全油门加速。
3. **结论**: 该改动属于自动化测试 Harness 与写实物理动力学匹配的必然要求, 符合整体架构设计。

工作分支 `antigravity/spin-fix`, 本轮针对人类复核指出的「第十七节上报 2.06g 与 grip.test.ts 断言 < 1.6g 全绿的硬矛盾」进行了彻底的根因排查与物理量化, 并补齐 600 帧坡道溜车物理机理诊断与弧长环回单元测试快照。

### 一、任务 1: 侧向加速度数据矛盾的彻底排查与更正

#### 1. 矛盾的核心排查结论与物理根因

经过逐行代码对比、动力学公式反解与多工况扫描, 查明矛盾产生的确切原因:

1. **两处代码计算的是否是同一个物理量?**
   - **答: 是同一个量**。`tests/unit/grip.test.ts` 与遥测探针均直接读取 `vehicle.lateralGripAccel`。
   - 其物理定义为: 四轮接地胎面侧向力矢量和除以整车质量 $a_{y,\text{grip}} = \frac{\sum_{i=0}^3 |F_{y,i}|}{m}$。计算公式完全一致, 不存在速度曲率加速度 vs 轮胎力加速度的定义失配, 也没有把重力在坡面上的分量漏算或误算。
2. **两处测试的工况是否存在差异? (核心根因)**
   - **答: 存在关键的入弯时间与赛道地形差异**:
     - **`grip.test.ts` (行 128)**: 采用 `makeCourse(1)` 自动驾驶预热 **25.0 秒** (1500 帧)。此时车辆位于 `arc = 750.8 m`。该处恰好是**平缓浅坡直道与缓弯过渡区**, 四轮垂直法向力合力 $F_z \approx 23.8\text{ kN}$ ($\approx 2.02\times$ 静态车重)。在随后 2 秒满舵转向中, 实测峰值侧向抓地加速度为 **$15.52\text{ m/s}^2 = 1.5825\text{ g}$**。
       - 由于 $15.52\text{ m/s}^2 < 1.6 \times 9.81 = 15.696\text{ m/s}^2$, **测试断言 `expect(peak).toBeLessThan(1.6 * 9.81)` 是真实被执行求值且真正绿灯通过的 (并非 skip 或 it.fails)**。
     - **第十七节探针测法**: 采用了 **20.0 秒** (1200 帧) 预热。此时车辆位于 `arc = 621.2 m`。该处恰好是**大下坡坡底与 29° 陡侧倾复合弯道 (bank = 0.5 rad)**。受下压力、离心贴地分量与下坡凹谷垂直压缩三重叠加, 四轮法向力 $F_z$ 激增至 **$40,360\text{ N}$ (静态车重的 3.43 倍)**。
       - 根据轮胎附着极限公式 $F_{y,\max} \approx \mu(F_z) \cdot F_z$, 在 $3.43\times$ 大垂直载荷下, 轮胎可输出高达 $24.3\text{ kN}$ 的侧向力, 换算至车身质量得到 $a_y = \frac{24300\text{ N}}{1200\text{ kg}} = 20.25\text{ m/s}^2 = \mathbf{2.064\text{ g}}$。

#### 2. 两个数值的真实属性与验收指标定义

- **「峰值侧向抓地 1.3 ~ 1.6 g」验收指标的真实物理含义**: 指的是**平地基准路面上 (无 3D 大侧倾、无垂直下坡凹陷压缩辅助) 的轮胎本征附着能力**。
  - 在平地 (`Heightfield`) 实测 80~100 km/h 满舵过弯, 峰值侧向抓地加速度为 **1.524 g ~ 1.629 g**, **真正满足 1.3 ~ 1.6 g 验收指标**。
- **2.06 g 测出的是什么?**: 测出的是 **3D 特种赛道在 29° 大侧倾弯道与下坡压缩凹谷处产生的超额地形贴地力** (与真实赛车在 Daytona/Monza 倾斜大椭圆弯道中因离心垂直压紧产生超 2.0g 抓地力的物理规律一致)。

#### 3. 同工况并排对照与第十七节数据更正表

| 工况 / 场景 | 入弯车速 | 峰值垂直法向载荷 $F_z$ / 车重比 | 实测峰值侧向抓地 $a_{y,\text{grip}}$ | 判定与验收状态 |

#### 2. 「缺驻车制动」还是「缺滚动阻力」的判定与建议方案

- **核心判定: 根本原因是「缺少轮胎滚动阻力物理项 ($C_{rr}$)」, 叠加「缺少驻车制动机制」**:
  1. **轮胎滚动阻力缺失 (底层物理)**:
     - 真实车辆轮胎橡胶在滚动受压过程中存在能量迟滞损失, 产生滚动阻力 $F_{rr} = C_{rr} \cdot F_z$ (沥青路面 $C_{rr} \approx 0.015 \sim 0.020$)。
     - 对于 1200kg 赛车, 滚动阻力约为 $F_{rr} \approx 0.015 \times 1200 \times 9.81 \approx 176.6\text{ N}$。
     - 当赛道坡度小于 $1.5\%$ ($\theta < 0.86^\circ$, 例如 Seed 42 为 0.88%、Seed 1337 为 1.11%、Seed 7 为 0.96%) 时, 重力下滑分量 $F_g = m g \sin\theta < 176\text{ N}$ 小于静滚动阻力。**真车在这些坡度上即使空挡不拉手刹也完全不会溜车**。
     - 当前代码中轮胎纵向力纯走 Pacejka 滑移率公式, 当 $\kappa \approx 0$ 时纵向阻力严格为 0, 导致车辆在任何非零微坡道上都会发生无阻尼自由滑动。
  2. **驻车制动缺失 (玩法机制)**:
     - 在更陡的坡道上 (例如 Seed 1 坡度 $2.59\%$, 重力下滑力达 $305\text{ N} > 176\text{ N}$), 真实空挡车辆确实会溜车, 赛车游戏通常在起跑倒计时期间引入手刹/驻车锁定。
- **修复建议 (留给人类拍板)**:
  - **方案 A (推荐, 补齐物理)**: 在 `tire.ts` / `vehicle.ts` 中加入轮胎滚动阻力 $F_{rr} = -C_{rr} \cdot F_z \cdot \tanh(\frac{v}{0.5})$ ($C_{rr} = 0.015$), 从物理根源消除 $\le 1.5\%$ 坡道自然溜车, 并使空挡滑行减速更加真实。
  - **方案 B (机制层)**: 在 `CAR` 中增加起跑驻车制动力矩 (`CAR.parkingBrakeTorque = 500`), 在玩家首次踩下油门前保持制动。

### 这一轮改了什么

**1. 转向上限按轮胎峰值侧偏角反推(e938266)**

人类反馈「打舵第一秒比按住之后狠」「松开 A/D 之后车还往那边多开一秒」。

实测 90 km/h 阶跃打舵:稳态前轮转角 0.42 rad,而 `TIRE.peakSlipAngle` 只有
0.10 —— 前轮被按在峰值的 3.7 倍上。打舵过程扫过峰值那一瞬 yawRate 冲到
0.61,滑过头之后稳态只剩 0.44,过冲比 1.39。

改成按「抓地极限侧向加速度 μ·g 对应的稳态偏航角速度是 a/v」反推:
`wheelBase·a/v² + peakSlipAngle·steerPastPeak`,低速由 `CAR.steerMax` 兜住。
删掉了按车速线性插值的 `steerAtTopSpeed`。回中速率单独拆成
`CAR.steerReturnRate`(9.0),打舵仍是 `steerRate`(4.5)。

结果:90 km/h 前轮转角 0.42 → 0.15 rad,稳态 yawRate 0.44 → 0.48
(**打得少了转得反而快**,证实之前在烧前轮);过冲比 1.39 → 1.29;
松键后 yawRate 从拖 2 秒变成 0.5 秒归零。

**2. 滚动阻力(1c56890)**

轮胎纵向力走纯滑移率模型,滑移率≈0 时阻力严格为 0,车在任意非零坡度上都会
无休止加速。补上 `F = -Crr·Fz·tanh(v/v0)`,Crr 0.015。零输入静止 10 秒:
seed 1337 从 5.30 km/h 且还在涨 → 收敛到 1.48;seed 42 从 2.44 → 0.35。

**3. 放开后轮空转让油门甩尾成立,然后又收回来一半(65e5cf8 → ca79a55)**

这是这一轮最曲折的部分,细节见下面「失败经验」。最终状态:
`TIRE.overdriveSlipMax = 2.4`,按**直线稳定优先**配的。

**4. 后轴按差速器约束配力(ca79a55)** —— 见下面「必须理解的不变量」新增一条。

### 必须理解的不变量(本轮新增一条)

**后轴左右的纵向力必须按差速器约束配,不能各按各的载荷算。**

差速器给两个半轴的扭矩相等(开式)或差额有上限(限滑),所以左右载荷不等只
体现为**转速**不等,不体现为**力**不等。如果每个后轮的纵向力按自己的载荷算,
载荷差 20% 力就差 20%,乘上半轮距直接凑出净偏航力矩 —— 这就是
`docs/tasks/spin-diagnosis.md` 里「一给油就原地打转」的根因。

实现在 `vehicle.ts` 阶段 3:后轴两轮的纵向力按轴平均载荷归一,**并按各自的
摩擦预算封顶**(不封会捅破摩擦圆,`grip.test.ts` 抓到过)。

**谁要动后轴的驱动力分配,先读这一条。**

**3. 拿混沌的验收测试当调参目标,拟合了噪声。**

## 第二十节:让甩尾成立(接第十九节,提交 #56)

这一节是现状。上一节交代的唯一未满意项是「甩尾不够」,这一节把它解决了,
并且**直线打转比上一版还稳**。手感好不好仍然由人类判断,下面全是实测数字。

### 一句话结论

甩尾出不来的主因不是空转不够,是**后轴上挂着一根它不该有的回正杠杆**:
`TIRE.casterTrail`(机械拖距)被四个轮子一起加上了。机械拖距是**主销几何**的
产物,后轮没有主销。拆掉它之后甩尾回来了,而直线稳定性改由**只在小侧偏角生效**
的气胎拖距提供 —— 那一项过了轮胎峰值侧偏角就归零,所以它压得住直线、压不到甩尾。

**「空转和直线打转是同一个旋钮」这件事到此为止。**

### 上一节点名的那条路我试了,是错的(先说这个,免得下一个人再走一遍)

第十九节推荐「发动机功率限制 + 挡位」,理由是「扭矩恒定、空转没有自限」。
**扭矩恒定这个观察是对的,但推出来的结论不成立**,算一遍就知道:

按现有阻力反推,极速 315 km/h 需要轮上约 470 kW。功率限制 `T = P/ω` 要开始咬,
得等 `ω > P/T_max = 470000/4400 = 107 rad/s`,换成车速是 **130 km/h 以上**。
而直线打转是**低速**病(seed 1 在起步头三秒发作),那里 ω 只有 30~60 rad/s,
功率限制根本够不着。挡位也一样:1 挡断油对应的轮速上限换算过去是 78 km/h 的
轮面速度,车在 10 km/h 时那仍然允许 κ≈10 的空转。

**功率限制会削的是高速那一段,而高速那一段恰恰是甩尾已经不够的地方**(见下面
120 km/h 那两行:下压力把抓地预算顶到超过驱动扭矩,后轮根本不空转了)。
所以它不是把两件事分开,是把仅剩的高速甩尾也削掉。这条我没有实现,只算到这里
就停了 —— 结论很确定,不值得再花一个窗口。

### 真正的根因(实测,分因过程完整)

`vehicle.ts` 阶段 3 的自回正力矩是 `sat = -(casterTrail + pneumatic) * fy`,
四个轮子一视同仁。量前后轴侧向力就露馅了:90 km/h 满油满舵稳态,
**前轴 10566 N、后轴 6292 N**。稳态过弯时两轴力矩必须平衡(轴距对称,a=b),
两边本该相等。差额 (10566−6292)×1.3 = **4168 N·m**,而四轮 SAT 合计
≈ **4251 N·m** —— 差额几乎全部由 SAT 解释。车不是不想转,是被自己摁住了。

而且 `casterTrail = 0.28` 和它自己的注释对不上:注释写 `r_wheel · tan(caster)`、
caster 取 5°~8°,`0.34 · tan(7°) = 0.042`。要凑出 0.28 得有 **39° 的主销后倾**。

分因用了两个场地,这是第十九节「失败经验」那一节的直接应用:

- **平地满油门直行 180 帧,峰值 yawRate = 0.00000**(五位小数)。底盘和驱动链
  完全对称,**没有不对称 bug 可修**。
- 所以赛道上那点偏航全部来自**地形扰动**,病因是「扛不住扰动」,不是「自己歪」。
  扛不住的原因也量清楚了:后轮被驱动力矩纵向顶穿之后,联合滑移把它的侧偏刚度
  打掉约 **8.8 倍**(κ=0.288 时 3.91·peak/rad,κ=0 时 34.2·peak/rad)。
  **这是真实物理,不是 bug** —— 真车靠牵引力控制或驾驶员收油避开,这台车两样都没有。

### 改了什么

1. **机械拖距只加在转向轮上**(`vehicle.ts` 阶段 3)。后轮只剩气胎拖距。
2. **`TIRE.casterTrail` 0.28 → 0.07**,按注释自己的公式取,对应 caster ≈ 11.6°(赛车量级)。
3. **`TIRE.pneumaticTrail` 0.10 → 0.45**,这是新的方向稳定器。
4. **`TIRE.mu0` 1.38 → 1.36**,把平地峰值侧向抓地拉回人类那条 1.3~1.6 g 区间内(下面有账)。
5. `TIRE.overdriveSlipMax` **没动**,仍是 2.4。它现在是留给人类的甩尾旋钮。

### 新增的不变量:两种拖距分工不同,别再把它们合并

| | 机械拖距 `casterTrail` | 气胎拖距 `pneumaticTrail` |
|---|---|---|
| 物理来源 | 主销(转向轴)几何 | 接地印痕侧向压力中心偏后 |
| 哪些轮子有 | **只有转向轮** | 四个轮子都有 |
| 随侧偏角 | **不衰减,永远在** | `max(0, 1-u)`,过峰值侧偏角后**严格为 0** |
| 因此它压住的 | 任何时候都在把车摆正 | 只在车快开直了的时候扶方向 |

**甩尾要的是后者不是前者。** 谁要动 SAT,先读这一条。

### 改了三处断言,逐条说明理由

判据仍是第十九节那条:守的是人类验收线,还是实现细节。

1. **`gripFlat.test.ts` 的 1.3~1.6 g —— 一个字没动,改的是参数。**

2. **`grip.test.ts`「侧滑之后车头会被拉回行进方向」:改成取窗口内最小值。**

### 追加(#57):100 km/h 附近太容易打滑

人类试玩反馈:「甩尾够了,但速度到 100 的时候有点容易打滑,其他的没问题。」

**量出来确实有个鼓包,而且峰值就在他说的那个速度。** 满油满舵稳态侧滑角:
60 km/h 是 9.33°、80 是 11.05°、**101 是 12.52°(全速域最大)**,再往上一步
120 就掉到 5.31°。

机制:满油门时后轮空不空转,取决于驱动力矩有没有超过后轴抓地预算 `μ·Fz_rear·R`。
Fz_rear 含下压力、随 v² 涨,所以存在一个**交叉速度**,过了它后轮不再空转、车立刻
变听话(后轮 κ 从 0.288 掉到 0.115 就是这个)。这个交叉点原来落在 110 km/h,
所以 100 正好卡在鼓包顶上。

**修法:`CAR.driveTorque` 4400 → 4000**,把交叉点从 110 挪到 95。

低速为什么不受影响:低速段扭矩超出预算的幅度极大(静止时 4400/2761 = 1.59),
而 `TIRE.overdriveSlipMax` 的钳位在超出 9.3% 之后就饱和了 —— 低速本来就顶在
钳位上,少 400 N·m 照样顶在钳位上。**这正是能做到「只动 100 那一档」的原因。**

| 入弯速度 | 改之前 | 改之后 |
|---|---|---|
| 60 km/h | 9.33° | **9.31°**(没动) |
| 80 km/h | 11.05° | **11.47°**(没动) |
| 100 km/h | **12.52°** | **4.88°** |
| 120 km/h | 5.31° | 4.39° |

顺带变好的两项(都是「少空转 = 多推进 / 多稳定」):

- 平地 0-100:3.60 s → **3.52 s**(起步是抓地限制不是扭矩限制,第十九节量过)
- 直线峰值 yawRate:seed 1 0.145 → **0.083**,42 0.037 → 0.025,1337 0.014 → 0.011
- 平地峰值侧向 @100 km/h:1.549 g,仍在 1.3~1.6 区间内

**试过但不行的两条,别再走:**

- **抬 `CAR.downforce`**:同样能把交叉点往下挪(它就是那个 v² 项),但它是靠**加载荷**
  做到的,直接把 100 km/h 的平地峰值侧向抓地顶穿人类那条 1.6 g 的线 ——
  5.5 → 7.5 就到 1.653 g。这条路被验收线堵死。
- **`driveTorque` 只降到 4200**:交叉点很陡,100 km/h 仍是 12.62°,等于没改。

**一个诚实的说明:鼓包是被挪走了,不是被抹平了。** 峰值高度基本没变(12.52° → 12.58°),
只是从 101 km/h 移到了 86 km/h。人类原本认可 80 km/h 的 11.05°,而 86 现在是 12.58°,
在他认可的那一档上多了约 1°。**如果他回头说「85 左右也有点滑」,那就是这件事**,
下一步是继续降 `driveTorque`:3600 会让 80 km/h 也塌到 4.11°(连他喜欢的那段一起没了),
所以真要抹平鼓包得换思路,不能再靠这个旋钮。

### 再追加(#58):鼓包不是被挪走,是被抹平

人类反馈:「的确 85 左右有点滑。」—— 这正是 #57 那一节自己预告过的事,
**降 `driveTorque` 只是把鼓包从 101 km/h 挪到 86,峰值高度一点没变。**

#### 真正的根因是 `TIRE.overdriveSlipGain` 太陡,它是个阶跃函数

滑移放大量是 `1 + gain·excess`,再由 `overdriveSlipMax`(2.4)封顶。gain=15 时
excess 只要超过 (2.4−1)/15 ≈ **9.3%** 就顶到钳位 —— 而全速域几乎处处超过 9.3%。
于是后轮滑移率恒为 0.288,**同一个滑移率在越高的车速对应越大的滑移速度**,
侧滑角就随车速一路涨,直到下压力把抓地预算抬过驱动力矩、瞬间掉下来。

**那不是「鼓包 + 悬崖」,那就是一个阶跃函数的两侧。** 挪它没有用,得把它抹平。

gain 调小之后 excess 不再瞬间饱和;而 excess 本身随车速下降(下压力在抬抓地
预算),两者相乘就得到一条平滑下降的曲线。

#### 改了什么

| | 旧 | 新 |
|---|---|---|
| `TIRE.overdriveSlipGain` | 15.0 | **6.0** |
| `CAR.driveTorque` | 4000 | 4000(#57 那次仍然需要,见下) |
| `CAR.wheelInertia` | 0.9 | **2.0** |

满油满舵稳态侧滑角(平地):

| 入弯 km/h | 40 | 50 | 60 | 70 | 80 | 90 | 100 | 120 |
|---|---|---|---|---|---|---|---|---|
| #56(最早) | 7.19 | 8.30 | 9.33 | 10.26 | 11.05 | — | **12.52** | 5.31 |
| #57 | 7.17 | 8.30 | 9.31 | 10.26 | 11.47 | 11.27 | 4.88 | 4.39 |
| **#58** | 7.16 | 8.43 | **9.70** | 9.06 | 7.75 | 5.92 | 4.92 | 4.38 |

**峰值回到 60 km/h(人类明确认可过的那一档),往上单调下降,鼓包没了。**

`driveTorque` 为什么不还原回 4400:实测 4400 + gain 6 会把鼓包搅回来
(70/81/90 = 10.32 / 11.60 / 11.50),而且平地峰值侧向顶到 1.574 g,贴着
1.6 g 的线。**两个改动是一套,不能只留一个。**

#### `wheelInertia` 0.9 → 2.0 是为了把 0-100 还回验收线

gain 降下来之后起步空转跟着少了,而**起步是抓地限制**的 —— 少空转等于多推进,
0-100 从 3.52 s 掉到 3.42 s,越过了 `vehicle.test.ts` 的下界 3.5。那条守的是人类
「起步太快、不写实」的反馈,**不能放宽,只能从物理这一侧补回来**。

选轮惯量而不是选降扭矩:实测它**只动起步,甩尾曲线一动不动**
(0.9 / 1.4 / 2.0 三档,50 km/h = 8.46 / 8.40 / 8.43,60 km/h = 9.68 / 9.69 / 9.70),
极速也不变(360 km/h)。降扭矩则会把刚抹平的鼓包搅回来。

2.0 站得住:这个量还得替**整条传动链折算到轮上的转动惯量**兜底(发动机+飞轮+
变速箱经齿比折算过来,低挡位下这一份往往比轮子本身还大),模型里没有单独的传动链惯量。

#### 试过但不行的:发动机功率限制(实现了,又删掉了)

第十九节点名、#56 那一节算过的那条路,这次**真的实现了一遍**
(`T = min(driveTorque, P/ω)`,低速扭矩平台 + 高速恒功率段),然后删掉了。

理由不是它不物理 —— 它很物理,还自带负反馈(空转让 ω 变大 → 扭矩变小 → 空转收敛)。
理由是**它同样只是把阶跃挪个位置**:

`overdriveSlipGain` 一个数就能真正抹平,就不引入这套机制了(宪法:不要顺手做)。
**下一个人如果又想到功率限制:它治不了这个,也治不了低速直线打转(#56 算过)。**

## 第二十三节:修复 Course.sample 弧长环回缺陷 (fix/arc-loopback, 2026-08)

工作分支 `fix/arc-loopback`, 切自 `claude/deepseek-task-allocation-oxuiuo` 提交 `0877193`。
本轮彻底修复了 `Course.sample` 在闭环赛道起跑线后方微小区间 $[-\epsilon, 0]$ 的弧长环回 (loopback) 缺陷, 改写了单元测试快照并补齐起跑线防刷圈与多 seed 验证, 四道质量门禁全部通过。

### 一、缺陷根因与现象

闭环赛道首尾线段在起跑线 (0 号采样点 `samples[0]`) 相连。当采样点落在起跑线正后方极小负向区间 $[-\epsilon, 0]$ 时:
- 空间索引投影将其匹配到最后一条线段 (segment $N-1$), 计算出的参数 $t \approx 1 - \frac{\epsilon}{\text{spacing}}$。
- 导致计算出的弧长 $arc = (N - 1 + t) \cdot \text{spacing} \approx \text{totalLength} - \epsilon \approx 2736\text{m}$, 而非 0 附近。
- 实测车辆在起跑线因悬挂自然沉降或坡道微小后溜 $0.00002\text{m}$ (20 微米) 即可触发, 造成 2736m 的弧长剧烈突变。

### 二、修法与设计抉择

在 `src/game/course.ts` 的 `Course.sample` 中:
- 当匹配段落在最后一段 (`bestRow === this.rows - 1`) 且距离终点/起点在保护窗口内 ($(1 - bestT) \cdot \text{spacing} \le 0.5 \cdot \text{spacing}$) 时, 将 `arc` 严格 clamp 为 `0`。

**【为何选择 clamp 到 0 而非允许小负值】**:
1. **数据结构与物理契约**: 赛道弧长定义域为非负实数 $[0, \text{totalLength}]$, clamp 到 0 保证了 $arc \ge 0$ 的非负不变量。
2. **防范下游负索引越界**: 下游模块 (如 `Race.trackCheckpoints` 与 `Autopilot.drive`) 广泛使用 `Math.floor(vehicle.arc / spacing) % count`。在 JavaScript 中负数取模仍为负数 (例如 $-1 \% 24 === -1$), 允许负 arc 会导致 `samples[-1]` 读取为 `undefined` 造成潜在运行时缺陷; clamp 到 0 彻底杜绝了负下标越界隐患。
3. **起跑线状态连续平稳**: 车辆在起跑线上静止沉降或微小后溜时, `arc` 稳定保持为 0, 前后过渡完全连续 ($\lim_{s \to 0^-} arc = 0 = \lim_{s \to 0^+} arc$), 不会产生圈数误判、漏圈或多圈。

### 一、幽灵回放:不存轨迹,只存输入

设计沿用 `core/input.ts` 里 `InputRecorder`/`RecordedInput` 那句已经写好的类注释——
「M4 的幽灵回放直接复用这份数据:幽灵不存轨迹,只存输入,靠同一个 seed 和同一套
物理重新算出来」。这一轮把它接上:

- `src/game/ghost.ts`(新):`Ghost` 类包一辆独立的 `Vehicle` + 一个只用来做
  出界重置的内部 `Race`(从不 `setSeed()`,不碰 localStorage)+ 一份复用玩家

  `bestSectorTimes` 一起存盘,并立刻喂给 `this.ghost` 让下一圈就能追自己刚跑出
  的这一圈;不管是不是新纪录,`recorder.clear()` + `ghost.restartLap()` 都会
  执行 —— 幽灵每圈都和玩家同时从起跑线出发,而不是自己按录制长度无限循环。
  出界重置(`Race.respawn()`)**不清空录制**:那次出界和被拽回来的过程要被
  幽灵原样重放出来。
- `src/game/records.ts`:`LapRecord` 加一个可选字段 `ghostInput`(`InputRecorder`

**踩到的一个坑,写下来免得下一个人重踩:`Vehicle.update()` 内部会调用一次

`World.physics`(和玩家共用一个 Rapier `World`),结果变成「一帧里玩家、幽灵

跟着遭殃,速度位移全部翻倍。两套车身本来就没挂碰撞体(见 `physics.ts` 类注释,
接地靠 `Course.sample()` 不是引擎碰撞体),所以修法是让 `Ghost` 拥有**自己独立
的 `Physics` 实例**,互不干扰。这个坑是在写 `tests/unit/ghost.test.ts` 的确定性
断言时发现的 —— 手动模拟「玩家跑一段、幽灵重放同一段」时数值对不上,查下去才

### 二、暂停/重开/换 seed 菜单 —— 一个需要人类确认的产品判断

`docs/PLAN.md` 原文是「开始菜单 / 暂停 / 重开 / seed 输入框」四件事列在一起。
**这一轮没有做成「开局必须先点掉的启动画面」**,理由是这么做会直接改掉两类
已经跑通、而且被人类看过确认的东西:

1. `tests/visual/smoke.spec.ts` 里「不带 test=1 时自行跑主循环」和「实时模式下
   seed 1/42/1337 正常渲染 HUD 与小地图」这几条,在页面 `painted` 之后**零交互**

   或者需要另外教会它们先点掉菜单 —— 而这几条测试本身就是在守「Pages 上线后
   真实用户看到的那条路径」。
2. 第二十四节里人类已经看过的 `smoke-realtime-seed{1,42,1337}.png` 这几张截图,
   拍的是「一进页面就能看到的画面」;加一块挡板会让同名截图从「赛道」变成

(赛道+地形+护墙网格要 2 秒多,见第四节性能数据),没必要为了换 seed 单独写一套
原地重建 `World` 的逻辑,跳转是现有「URL 参数决定 seed」路径的自然延伸。

**这是一个需要人类确认的产品判断,不是「做不到」而是「选了风险最小的一种读法」**——
把它写清楚留给人类拍板:如果确实想要开局必须先点掉的传统启动画面,需要同步
更新上面两类测试的断言方式(比如先发一次点击/按键再断言)和对应的截图基准,
这是下一轮可以单独做的小工作,不困难,只是这一轮判断没必要在没问清楚之前
顺手把已经验收过的东西改掉。

新增 `src/game/menu.ts`(`Menu` 类,DOM overlay,和 `Hud` 一样不在 canvas 里
排文字)。`Hud` 的操作提示文案加了 `· Esc 暂停`。`style.css` 补了

## 第二十七节:M5 起步 —— 程序化音频(2026-08)

第二十六节的 PR(#9)人类已经合并进 `main`。M4 到此全部完成。人类选下一步方向
时选了「M5 剩余」,而 M5 本身又拆成四块相对独立的工作(精选赛道+主题、程序化
音频、加速带/跳台/隧道段、主音量与 `prefers-reduced-motion`)—— 问过人类先做
哪一块,选的是**程序化音频**:不碰赛道生成/物理,风险最低,而且是当时唯一还
完全空白的子系统(`src/audio/` 之前只有一份占位 README)。

### 一、做了什么

新增 `src/audio/`,五个文件,全部 Web Audio API 程序化合成,**零音频文件**:

- `context.ts` —— `AudioBus`:唯一的 `AudioContext` + 主音量总线。音量/静音
  存 localStorage(key `driftline:audio`),和 `records.ts` 的持久化不是一套
  存储(没必要绑同一个 seed,音量是全局偏好)。
- `engine.ts` —— `EngineSound`:锯齿波过一个随速度调制的低通滤波器,不是采样
  循环。频率/滤波截止/音量三个参数按 `REFERENCE_TOP_SPEED` 线性映射,松油门
  滑行音量降到 30% 而不是归零(引擎还在转)。
- `wind.ts` —— `WindNoise`:一段预生成的白噪声循环(用注入的 `Rng`,不调
  `Math.random()`)过低通滤波器,音量和截止频率都随速度涨。
- `impact.ts` / `ui.ts` —— 撞墙音 / UI 点击音,事件驱动的一次性脉冲,用完即扔
  (不在每帧路径上,不违反「每帧不分配对象」)。撞墙音的强度直接读
  `Vehicle.wallImpact`(0..1,当帧撞墙强度,没撞是 0,不需要自己做边缘检测)。
- `director.ts` —— `AudioDirector`:`main.ts` 唯一直接接线的入口,拼装引擎音
  + 气流噪声两个持续声源,每个固定步调一次。

数值全部集中在 `tuning.ts` 新增的 `AUDIO` 段,和其余六段(`VEHICLE`/`CAMERA`/
`TRACK`/`SKY`/`CRAFT`/`POST`)同一个来源。

**接线到 `main.ts`**:测试模式不构造 `AudioDirector`(`?test=1` 下没有真实用户
手势,`AudioContext` 起不来,和 `Hud`/`Menu` 同一条约定)。浏览器自动播放策略
要求先有一次真实用户手势才会真正出声——`AudioContext` 造出来是 `suspended`
的,`main.ts` 监听首次 `keydown`/`pointerdown` 调一次 `audio.resume()`,监听器
自己摘掉自己。

**接到 `Menu`(第二十六节那个 Esc 暂停菜单)**:菜单卡片里加了一行音量滑块 +
静音按钮,构造时读 `audio.masterVolume`/`audio.muted` 预填,拖动/点击回调进
`AudioDirector`。继续/重开按钮点击时顺手 `audio?.triggerUiClick()`,菜单第一次
有了自己的音效反馈。

### 二、这一轮唯一的产品判断:`prefers-reduced-motion` 没做

PLAN.md 原句是「主音量与静音,尊重 `prefers-reduced-motion`」。**这一轮只做了
「主音量与静音」,没有碰 `prefers-reduced-motion`,这是这一轮自己做的取舍,
没有单独问过人类,写在这里等确认。** 标准语境里 `prefers-reduced-motion` 管的
是**视觉**动画(相机滚转/FOV 突变这类),不是音频音量;如果字面上把它塞进音频
这一块,最直接的落点会是改 `ChaseCamera` 的滚转/FOV 效果 —— 那是人类已经验收
过的手感/观感的一部分(第十九、二十节),这一轮判断不该在没问清楚范围之前
顺手碰,留给做「加速带/跳台/隧道段」或专门一轮视觉打磨时,和人类确认过范围
再处理。

### 四、踩到的一个坑:`window.localStorage` 在 Node 测试环境里直接抛错

第一版 `context.ts` 的 `loadSettings`/`saveSettings` 直接写 `window.localStorage`。
写单测时(`AudioBus` 的持久化那条)发现存进去的值读不出来 —— 查下去是
`window` 在 vitest 的 `node` 环境下压根不存在,`window.localStorage` 直接抛
`ReferenceError`,被 `try/catch` 悄悄吞掉,音量偏好因此永远存不下也读不出来,
**而且不会有任何测试变红**(如果没有专门为持久化写单测的话)。

`records.ts` 的 `getStorage()` 早就用「先判 `typeof window !== 'undefined'`,
再退到 `globalThis.localStorage`」这套写法处理过同一个问题(见第二十二节
`setStorageEnabled` 那条讨论,以及 `records.ts` 本身的实现)。`context.ts` 现在
改成同一套写法,并补了单测(`audio.test.ts` 的 `AudioBus` 持久化那条)守住它。
**教训:这个项目里任何新写的 `localStorage` 访问,都先去抄 `records.ts` 的
`getStorage()`,别自己直接写 `window.localStorage`。**

## 第二十八节:精选赛道 + 一个已经上线的严重 bug(2026-08)

紧接第二十七节,同一轮会话里继续做 M5 的「精选赛道+主题+目标时间」,过程中
**发现并修了一个已经合并进 `main`、正在 Pages 上线跑的严重 bug** —— 优先级
比继续加新功能高,记在最前面。

### 一、严重 bug:暂停菜单从第一帧就盖住整个游戏

**现象**:第二十六节加的 Esc 暂停菜单,`Menu` 构造时 `root.hidden = true`,
逻辑上应该默认不可见。但 `style.css` 里 `.menu-overlay { display: grid; ... }`
没有对 `[hidden]` 开后门,而 `.menu-overlay` 和浏览器 UA 样式表的
`[hidden] { display: none }` 选择器特异度打平(都是 (0,1,0)),**源码顺序
在后的赢** —— 也就是自己写的 `display: grid` 压过了 `hidden` 属性,菜单
**从第一帧就盖在整个游戏上面**,而不是等玩家按 Esc 才出现。

这条从 PR #9(第二十六节)合并进 `main` 起就在线上,`npm run dev` 或 Pages
打开就能看到:标题「已暂停」的卡片糊在画面正中央,canvas 在它后面继续跑但
被完全挡住 —— 这不是「暂停功能」,是「整个游戏被一直锁着」。

**为什么两轮四道门都没测出来**:

1. `npm run shoot`(以及本节之前所有靠它产出的截图)默认走 `?test=1`,
   而 `Menu` 在测试模式下**根本不构造**(和 `Hud` 同一条约定)——这条路径
   永远看不到这个 bug,不管截多少张图。
2. **唯一会构造 `Menu` 的路径**是 `test:visual` 套件里「实时模式下 seed
   1/42/1337 正常渲染 HUD 与小地图」那三条,但它们只断言 `#readout`(HUD
   的根节点,和 `#menu-overlay`是两个不同的 DOM 节点)的文本内容和亮度方差,
   从没检查过页面上还叠着别的东西。
3. 第二十六节自己写的 Esc 菜单测试,判定「菜单开没开」用的是
   `document.getElementById('menu-overlay').hidden` 这个 **DOM 属性**——
   `hidden` 属性确实被设成了 `true`(JS 逻辑是对的),只是 CSS 没听它的。
   断言和 bug 完全不在同一层,必然测不出来。
4. **我自己也没有实际去看一眼「实时模式、没按 Esc」时的截图**——第二十六节
   验证时只看了 `smoke-pause-menu.png`(那张图本来就该显示菜单)和
   `npm run shoot` 产出的图(测试模式,menu 不存在),唯一能照见这个 bug 的
   `smoke-realtime-seed1.png` 就在硬盘上,我却没有在合并前打开看过。

这是这个项目反复吃过的同一类亏(见 HANDOFF 第五节标题:「只有看图才能发现」),
这次的教训更具体一层:**「有截图产出」不等于「看过能照出这个 bug 的那张」**,
自动化流程里默认走的测试模式恰好是这个 bug 的盲区。

**是怎么发现的**:给刚做完的 M5「精选赛道」功能拍一张实时截图核对 TARGET
行时,顺手打开的那张图里菜单赫然在目——不是靠专门去找,是做别的验证时
撞见的。

**修法**(`style.css`):加一条 `.menu-overlay[hidden] { display: none; }`,
特异度 (0,2,0) 才压得过下面的 `.menu-overlay { display: grid }`。同时把
`tests/visual/smoke.spec.ts` 里 Esc 菜单测试判定「开没开」的方式从读
`.hidden` 属性改成读 `getComputedStyle(overlay).display`——**这条新断言
实测验证过真的能拦住这个 bug**:临时把 CSS 修复 `git stash` 掉、只保留新
断言,测试确实红了(`Expected: false, Received: true`),复原修复后再跑
就绿,证明不是碰巧。

### 二、精选赛道 + 主题 + 目标时间

M5 剩下三块里的第二块。`generateTrack()` 保证任何 seed 都能生成出合格赛道,
但合格不等于有代表性——退化成近似正圆的赛道也合格,这份精选列表就是从一批
候选里挑出更有代表性的几条。

**新增 `scripts/curate-tracks.ts`**(纯测量脚本,不改任何生成器/物理参数):
扫一批候选 seed,筛 `layout.attempts === 1`(第一次就通过校验,弯道形状没被
「收紧幅度」这个兜底机制修剪过)且总长落在 2.6~3.8 km,按三套环境主题
(`gfx/palette.ts` 的 `THEMES`)分组各挑几条,再用 `Autopilot`(M2 的验收
循迹器,保守、不甩尾)实际跑一圈量出基线圈速,目标时间 = 基线 × 0.82。
`npm run curate-tracks -- --range=500 --perTheme=2` 跑出候选,人工从输出里

### 二、载具极速校准:找到真正的旋钮

**第一次尝试(错的)**:`CAR.dragArea` 0.7→1.45(解方程猜的,期望翻倍阻力
系数把极速砍掉一截)。实测极速只从 360km/h 掉到 356km/h,几乎没用。

**查代码才发现真正在起作用的是 `vehicle.ts:563` 的轮速上限**:

```ts
const maxSpin = (REFERENCE_TOP_SPEED * 1.15) / CAR.wheelRadius;
```

车的极速根本不是靠「驱动力 vs 阻力」的平衡点自然长出来的,是被这条硬上限
直接钳住的——旧的 `REFERENCE_TOP_SPEED=88`(→316.8km/h 上限)恰好和实测的
360km/h 在同一量级,阻力系数翻倍对已经被钳死的速度上限没有意义。

**改法**:把 `dragArea` 改回 0.7(撤销第一次的误改),转而调
`REFERENCE_TOP_SPEED`。因为 `maxSpin` 按 `REFERENCE_TOP_SPEED × 1.15` 算,
要让实测极速落在 A110 的 250km/h,`REFERENCE_TOP_SPEED` 本身要设成
250/3.6/1.15 ≈ 60.3,不是直接设成 250/3.6=69.4(那样实测会到 285km/h,
因为 1.15 倍的余量还在)。

实测:`REFERENCE_TOP_SPEED: 88 → 60.3`,极速 360 → **248 km/h**(目标 250,
误差不到 1%)。**这一步单独做,drift-probe 的甩尾/打转数字逐位不变**——
`REFERENCE_TOP_SPEED` 只钳轮速上限,不进入任何抓地力/滑移率的计算路径,
是这一轮唯一"零副作用"的旋钮。

`REFERENCE_TOP_SPEED` 还被 `chaseCamera.ts`(FOV/滚转随速度增益)、
`autopilot.ts`(过弯减速判断)、`audio/director.ts`(引擎音/气流音随速度
增益)、`ghost.ts`/`world.ts`(尾灯亮度随速度增益)引用,全部是
`normalize01(speed, 0, REFERENCE_TOP_SPEED)` 这种归一化写法,改这一个常量
会让它们的"满值"对应的实际车速一起往下移,是预期内的联动,不用逐处改。

### 三、载具加速度校准:一个真实冲突,不是调参问题

目标 0-100 从实测 3.62s 拉到 A110 的 4.5s,直觉旋钮是 `CAR.driveTorque`
(4000 N·m)。实测这条路走不通:

| `driveTorque` | 0-100 | 入弯 60 稳态β / 峰值β | 入弯 100 稳态β / 峰值β |
|---|---|---|---|
| 4000(原始) | 3.62s | 9.70° / 14.94° | 4.92° / 7.14° |
| 3200 | **3.55s**(反而更快) | 2.66° / 2.82° | 2.81° / 4.36° |
| 2800 | 3.60s | (未详测,量级同上) | — |
| 2000 | 3.90s | 0.65° / 0.85° | 1.12° / 1.29° |
| 1450 | 4.52s(达到目标) | **0.08° / 1.03°**(甩尾基本消失) | 0.68° / 0.71° |

**两个反直觉的发现**:

1. **扭矩降到 3200(仅比原始少 20%)时 0-100 反而从 3.62s 变快到 3.55s。**
   起步阶段驱动力矩本来就远超后轴抓地预算(是"抓地限制"不是"扭矩限制",
   HANDOFF 第十九节已经量过这条),降一点扭矩只是减少了空转浪费的那部分,
   净推进反而更多。这条路径上真正影响 0-100 的扭矩区间,比想象的窄得多、
   低得多。
2. **要让 0-100 真的变慢,必须把扭矩压到接近静态抓地预算的量级
   (mu0×后轴静载×轮半径 ≈ 2722 N·m 那个数量级附近),而这个量级也正是甩尾
   机制赖以存在的"驱动力矩超过后轴抓地预算"这件事本身——扭矩一旦不再明显
   超预算,车就再也不会一给油就甩尾了。** 这不是"甩尾变淡了一点",是从
   9.70° 掉到 0.08°,基本等于关掉了这个游戏最核心、人类反复验收过的手感。

**结论:0-100 的写实目标和已验收的甩尾手感,在 `driveTorque` 这一个旋钮上
是同一件事的两面,物理上没法同时满足。** 已经问过人类,甩尾手感优先级更高,
所以 **`driveTorque` 维持原值 4000,0-100 保持约 3.62s,不追 A110 的 4.5s**。
这台车现在是"直线比真实 A110 快,但不会像真车那样轻易靠油门甩起来"——
两件事都不真实,但选的是对已验收内容伤害最小的那一种不真实。

### 决定

问了人类怎么处理,给了三个选项(全删/只留隧道删跳台加速带/三样都做),人类
选了**全删**,并加了一句"但是需要极致的和现实贴合"——理解为这条决定本身要

### 为什么这个决定站得住(不是各打五十大板的和稀泥)

- **跳台、加速带**:这两样是拉力赛(WRC)、越野赛、卡丁赛道的元素。这个项目

  赛道内容。跳台/加速带留着,会让"现实参照"这条主线在赛道内容层面站不住。
- **隧道**:唯一一个三选项里*有*真实依据的——摩纳哥大奖赛(Monaco Grand
  Prix)赛道有一段真实隧道(Tunnel de Monaco/Fairmont Hairpin 到 Nouvelle
  Chicane 之间)。但人类的诉求是"极致贴合现实",而不是"只要能编出一个现实
  依据就行"——隧道要做到不违和,需要额外的光照/曝光突变处理(从隧道外强光
  突然进隧道,真实赛车摄像机会有明显的自动曝光过渡,不是简单几何遮挡就够),
  这本身是一块新工作量,不是"反正已经在做赛道就顺手加一段"能糊弄过去的。
  权衡后跟人类一起定了**不逐个挑,三样一起砍**,把这块预算留给已经在验证

## 第三十三节:人类听感反馈 —— 撞击音不分强度,引擎音"怪"待确认(2026-08)

### 起因

人类在等 PR #13 CI 的时候提了两条听感反馈:「不同速度撞击墙面的声音都
一样」「引擎声音也有点怪怪的,频率之类的」。这是第二十七节标注的确认点
之一("音效数值完全是拍脑袋定的,没人耳听过、调过"),第一次拿到真实反馈。

### 撞击音:核查属实,不是主观感受问题,是真 bug

翻 `src/audio/impact.ts` 确认:`playImpact(bus, strength)` 只有 `gain`
的峰值跟着 `strength` 缩放,振荡器频率(固定 55Hz)、滤波截止频率(固定
`AUDIO.impactFilterFreq`)、包络时长(固定 `AUDIO.impactDuration`)全是
常量。轻轻蹭一下和正面高速撞墙,放出来的是**同一个声音,只是音量不同**——
人类是对的,这不是"听感偏好"层面的意见,是这几个参数从一开始就没跟着
撞击强度走。

还发现一个旁证:`tuning.ts` 里 `AUDIO.impactGain` 那段的注释写的是
「撞墙音:一次性的**噪声**脉冲」,但 `impact.ts` 的实际实现从始至终是一个
纯振荡器(方波),从没用过噪声。这条注释像是最初设计就想做噪声撞击音,
写完注释之后实现的时候换成了更简单的振荡器,注释没跟着改——两边对不上。

**修的方式**:`impact.ts` 从自由函数改成 `ImpactPlayer` 类(仿 `WindNoise`
持有一个构造时预生成的噪声缓冲,理由同 `wind.ts`:撞墙可能连续好几帧触发,
没必要每次都现造一段新随机数据)。现在音高、滤波亮度、衰减时长、噪声混合
音量四个维度都跟 `strength` 走(新增 `impactToneFreqMin/Max`、
`impactFilterFreqMin/Max`、`impactDurationMin/Max`、`impactNoiseGain`、
`impactNoiseDuration`,见 `tuning.ts` AUDIO 段),同时把 `tuning.ts` 那条
过时注释改成和实现一致。`AudioDirector` 里 `wind`/`impact` 各自 `rng.fork()`
一份(以前只有 `wind` 用 `rng`,现在两个消费者不能共用同一条随机数流)。

`tests/unit/audio.test.ts` 里 `describe('playImpact', …)` 换成
`describe('ImpactPlayer', …)`,新断言四个维度都随强度变化,不再只测
音量。四道门:`typecheck` 0 错误,`test -- --run` 274 passed(基线 272,
+2)。`build` 通过。这次改动不涉及画面,没有额外跑 `test:visual`/`shoot`——
PR #13 的 CI 会跑到,不重复劳动。

### 引擎音:找到一个有依据的候选问题,但没法自己验证,还在等人类确认

`src/audio/engine.ts` 里频率只跟 `speed01` 走(`lerp(engineIdleFreq,
engineMaxFreq, speed01)`),`throttle` 只影响音量(`throttleFactor`),完全
不影响音高。这意味着:定速滑行时深踩一脚油门,声音只会变响,音高纹丝不动;
松开油门高速滑行,音高照样钉在跟车速对应的高位。真实发动机不是这样——
给油门时转速会先于车速往上蹿(尤其起步瞬间),松油门滑行时转速会往怠速
方向掉,不管车速多少。这可能是"频率怪"的一个来源,但只是一个候选,不是
确诊——**没法靠读代码确认"怪"具体怪在哪**(音域太窄?太像蜂鸣器?音色单薄?
还是真的就是这个"不跟给油联动"的问题?),CLAUDE.md 明确这条归人耳判断,
贸然改了猜不中还可能改差。已经在对话里问人类确认,这一节先记下候选原因和
没动代码的理由,等回复。

### 引擎音:人类确认了两条都是——补上转速代理 + 振荡器厚度

问过之后人类选了两条:「不跟给油联动」(问题里的候选)+「音域/音色不对」。
两条分开处理,信心程度不一样:

- **不跟给油联动(高信心,机制性问题,不是猜音色):** `engine.ts` 加了
  "转速代理"`rpm01 = speed01 * engineSpeedTrack + throttle * engineThrottleTrack`
  (两个权重加起来等于 1,车速与油门都拉满时和原来的顶速行为对齐),频率/
  滤波截止/音量三个映射全部从 `speed01` 换成这个 `rpm01`。现在定速滑行深踩
  一脚油门,音高会跟着往上走;松开油门高速滑行,音高会往下掉,不再钉死在
  车速对应的高位。
- **音域/音色不对(低信心,纯粹是猜,没法验证):** 单个纯振荡器听起来容易
  像合成器测试音,不像发动机的多缸声部叠加。加了第二个振荡器,频率是主振荡器
  的 `engineDetuneRatio`(1.008)倍——两个频率相近但不同的锯齿波叠加会有
  拍频,听感上比单个振荡器"厚"。混音比例 `engineDetuneMix = 0.55`,过同一个
  滤波器再求和,不单独控制亮度。**这条没有信心,只是"单振荡器听起来单薄"这个
  合理但没法自证的猜测**——`engineIdleFreq`/`engineMaxFreq` 这两个决定音域
  的数字这一轮没动,不确定"音域不对"具体是指整体音域偏移还是就是音色单薄的
  问题,如果加了振荡器厚度之后人类还是觉得音域不对,下一步应该是具体问
  "偏高还是偏低""跟哪个真实声音比"而不是继续猜数字。

**改动**:`src/audio/engine.ts`(rpm01 混合、第二振荡器/`detuneGain` 节点)、
`src/game/tuning.ts`(新增 `engineSpeedTrack`/`engineThrottleTrack`/
`engineDetuneRatio`/`engineDetuneMix`)、`tests/unit/audio.test.ts`(新增
3 条:同速度深踩油门音高涨、高速松油门音高比满油门低、失谐振荡器频率比例
正确)。四道门:`typecheck` 0 错误,`test -- --run` 277 passed(基线 274,
+3),`build` 通过。**这次改动同样不涉及画面**,没有额外跑 `test:visual`。

**没法自己验证的部分,原样写清楚**:这一节两处改动都没有真实听过——项目里
没有任何工具能让我"听"音频,`npm run dev` 需要人类在真实浏览器里打开。
提交前只能确认合成公式的方向对(该涨的涨了、该跟的跟了),不能确认"好听"。
这是 CLAUDE.md「人类验收点」的音频版本,还是需要人类实际听一遍反馈。

## 第三十四节:M7 第一块——把 `physics.step()` 从 `Vehicle.update()` 搬出来(2026-08)

### 起因

PR #13 合并、M5 正式收尾之后,人类说"好了之后可以继续做",睡前又交代
"不要问问题、按判断做、保证用完额度前先提交"。M7 架构草案(`docs/PLAN.md`
第 98-120 行)自己点出了最容易出错的一块:多车共享同一个 `Physics` 世界
和 `Ghost` 的独立世界方案正好相反,`physics.step()` 大概率要从
`Vehicle.update()` 里搬出来,变成 `World` 每帧显式调一次。这一节做的就是
这一件事——**只做这一件事**,不牵连 AI 逻辑、赛制、HUD 名次这些还没设计
的部分,理由和这一轮的额度交代一致:先把最容易出错、影响面最大的地基做对、
验证过,再往上叠。

### 现状核实:为什么这是真问题,不是臆测

`ghost.ts` 第 27-29 行的类注释已经把机制写得很清楚:`Vehicle.update()`
内部调一次 `physics.step()`;如果两辆车共用同一个 Rapier `World`,
`World.update()` 里对每辆车各调一次 `vehicle.update()`,这个世界一帧内就
被推进了两次,等于游戏在跑二倍速物理。这就是为什么 `Ghost` 现在造了一个
自己的、独立的 `Physics` 实例(`this.physics = new Physics()`)而不是复用
玩家的世界——不是为了"车与车不该碰撞"这个产品决策(那是对的,幽灵确实不该
被撞),而是**没有别的办法让两个 `Vehicle.update()` 共存于同一个世界**。
M7 要多车真碰撞,这条路走不通,必须先把 `step()` 的调度权拿出来。

### 改动:三段拆分,单车行为原样保留

`src/game/vehicle.ts`:`update(input, dt)` 从"一个大函数"拆成三段:

- `applyForces(input, dt)`:原来 `update()` 里 `physics.step()` **之前**的
  全部内容(清力、悬挂采样、轮胎力求解、气动力),不读回、不推进物理世界。
- （物理世界推进——不再是 `Vehicle` 的方法,由调用方决定什么时候调
  `physics.step()`。）
- `readState(dt)`:原来 `update()` 里 `physics.step()` **之后**的全部内容
  (读回刚体状态、`writeBack()`、`resolveWall()`、遥测帧提交)。
- `update(input, dt)` 现在只是三行:`applyForces()` → `physics.step()` →
  `readState()`,原样拼起来——**任何现有调用方(`Ghost`、单测、
  `drift-probe.ts`/`curate-tracks.ts` 这些脚本)一个字都不用改**,行为和
  拆分之前完全一致,因为执行顺序没有变,只是把同一段代码从一个方法体搬进
  了三个方法体。

`src/game/world.ts`:玩家这条路径不再调 `vehicle.update()`,改成显式的
`vehicle.applyForces() → this.physics.step() → vehicle.readState()` 三行,
证明"外部调度 `step()`"这条路真的走得通,而不只是 `Vehicle` 里多出来两个
没人用的方法。**这一步之后,`World` 有且仅有一辆车,行为必须和调
`update()` 完全一样**——这是本轮验证的核心断言。

### 验证:确定性基准值没有变

`tests/unit/physics.test.ts` 钉的那组基准值(CLAUDE.md 明确写了"这条测试
哪天红了不要放宽它,只有求解器动过一种可能")跑过了,连同 `vehicle.test.ts`
`grip.test.ts`/`gripFlat.test.ts`/`diagnostics.test.ts`/`race.test.ts`/
`raceTiming.test.ts` 这些依赖车辆物理的文件,共 50 条,全部原样通过——
拆分前后对单车路径是**行为完全等价**的重构,不是"应该等价",是测出来的。

四道门:`typecheck` 0 错误;`test -- --run` 277 passed(和 PR #13 合并后
持平,这一轮没加新用例,是纯重构,靠已有的基准值测试守住);`build` 通过;
`test:visual` 见下方结果。

### 下一步(没在这一轮做)

这一节只解决了"`step()` 能被外部统一调度"这一件事。M7 剩下的、体量更大的
部分(AI 车辆生成、多车 `applyForces()`/`readState()` 循环、车间碰撞响应、
发车队形、名次计算、终点结算、HUD 加名次)一个字都没动——按人类"睡前交代
不要用完额度"的要求,这一轮先把地基这一块做完、验证过、提交上去,不在
同一轮里往上叠更多没验证过的东西。

做"的顾虑写清楚了,现在人类醒着、明确要求做,就按上一节列的风险点动手:
给 `Physics.createChassis()` 挂真正的碰撞体,让车与车能共享同一个
`Physics` 世界并互相碰撞。

### 做了什么、怎么核实的

**`src/game/physics.ts`**:`ChassisSpec` 加了 `restitution`/`friction` 两个
字段,`createChassis()` 现在会额外挂一个 `RAPIER.ColliderDesc.cuboid(...)`
——密度设成 0,不叠加碰撞体自己那份质量(质量和惯量继续显式给,这条
不变量没变);碰撞组打包成只和别的车身碰撞体互相作用,和"地面接触不走
碰撞体"这条既有不变量不冲突(那条管的是 `Course.sample()` 那条查询路径,
这是完全独立的另一条路径)。`tuning.ts` 的 `CAR` 加了
`collisionRestitution: 0.15` / `collisionFriction: 0.35`,按真实车身碰撞
的量级估的(保险杠不怎么弹、车身蹭着车身有摩擦但不咬死),**没有实测,
标注了需要人类撞一次确认**——和甩尾参数同一类,机器判断不了"像不像"。

新增 `tests/unit/collision.test.ts`:两辆车共享一个 `Physics`,横向间距
故意小于车宽让碰撞体第一帧就重叠,断言(1)会被推开、不再穿模,
(2)分开过程数值不发散,(3)同样的初始状态跑两次结果一致。三条都过。
更关键的是:**跑了一遍完整的 277 条既有单测,逐条原样通过**——这证明
单车路径(唯一碰撞体、没有对手可撞)加了这个密度为 0 的碰撞体之后,
动力学完全没被扰动,已经钉住的基准值一个没动。

### 新一轮音频反馈(人类实际听过 `npm run dev` 之后)

PR #13 那版引擎音/撞击音修复**没有解决问题**,人类给了具体描述(不是笼统
的"奇怪"):

- **引擎音**:音色太电子/太糙、转速范围听不出来、有奇怪的颤音/干涉感。
  診断:`src/audio/engine.ts` 现在的做法是主振荡器(sawtooth)+ 一个按
  `engineDetuneRatio`(1.008)失谐的副振荡器叠加"增厚"——**两个频率相近
  的音源叠加会产生拍音(beating),这正是"颤音/干涉感"的来源,不是玩家
  幻听**。这个技巧适合合成器 pad,不适合引擎音。转速范围窄(62~210Hz,
  不到两个八度)也是实打实的——人耳对数感知音高,这个跨度确实听不出
  "转速往上冲"的推背感。
- **撞墙音**:太软/太闷没有硬物撞击感、音调太低沉听起来空心。
  診断:`src/audio/impact.ts` 现在音调层用的是 **square 波**(只有奇次
  谐波,音色学上就是"空心"音色的来源,单簧管那种),频率 42~85Hz 也确实
  偏沉;而且音调层的增益(`impactGain=0.5`)比噪声层(`impactNoiseGain=
  0.35`)还高、时长还长(0.1~0.22s vs 噪声固定 0.07s)——**该是主角的
  噪声"碎裂"分量反而是配角**,难怪整体听感是"闷响的球"而不是"硬物撞击的
  crack"。

这一轮**没有动手改这两处**——人类决定换到新窗口用 Opus 处理,交接提示词
见对话记录 / 下面这条。这里只留诊断,不留没验证过的改动,避免下一个窗口
还要重新读一遍代码才能确认症状。

### "左下角 #84 是什么"

`vite.config.ts` 的 `buildId()`:`` `#${git rev-list --count HEAD} ${短
sha}` ``,是本地构建时的**提交计数**,不是 GitHub 上的 PR/issue 编号。
人类看到的 84 就是他们本地跑 `npm run dev` 时那次构建对应的提交深度,
和 GitHub 上的 PR 号(现在到 #14)是两套不相关的编号。

### 引擎音:删掉失谐增厚,换成谐波谱 + 噪声层

第三十七节的诊断("失谐副振荡器 → 拍频 → 颤音/干涉感")成立,而且不需要靠
听觉验证——两个频率相近的音源叠加产生拍频是定义性的,拍频速率就是频率差,
`1.008 × 62Hz` 的差约 0.5Hz,正好落在人耳对振幅调制最敏感的区间。三条反馈
分别这么处理:

- **颤音/干涉感 → 整个"失谐增厚"实现思路删除。** `engineDetuneRatio` /
  `engineDetuneMix` 两个参数、`oscDetune` / `detuneGain` 两个节点全部移除。
  现在只有一个振荡器,单测 `只有一个振荡器…` 把这条钉死了。
- **音色太电子/太糙 → sawtooth 换成自定义 `PeriodicWave`。** 锯齿波的谐波是
  严格 1/n 的平滑衰减且一个不落,这个频谱形状就是"合成器测试音"的来源。新的
  `AUDIO.engineHarmonics`(12 项)故意做成不单调的——第 4 次谐波比第 3 次高,
  模拟排气管驻波——高次衰减也比 1/n 快。所有分量都是基频的严格整数倍,彼此
  锁相,**叠加只改变波形不产生拍频**,这是它和被删掉的失谐方案的本质区别。
- **转速范围听不出来 → 音域从 1.76 个八度拉到整整 3 个八度。**
  `engineIdleFreq` 62 → 45,`engineMaxFreq` 210 → 360(360 = 45 × 2³)。低通
  区间也跟着放宽(350/2600 → 420/3800)。这条是量得出来的,不是听感偏好:
  人耳对音高是对数感知的,不到两个八度撑不起"转速往上冲"。单测断言音域
  ≥ 2.5 个八度。

另外补了一层**排气粗糙度噪声**(带通,中心频率跟转速代理走,
`engineNoiseIdleGain` 0.012 → `engineNoiseMaxGain` 0.05)。理由:纯周期波形
无论谐波多丰富,每个周期都完全一样;真实发动机每个工作循环都有湍流与燃烧的
随机差异。**这才是失谐振荡器本来想解决的问题的正确解法。**

`EngineSound` 因此多了一个 `Rng` 构造参数(预生成噪声缓冲,和 `WindNoise`
同一套做法),`AudioDirector` 里三个消费者各 `rng.fork()` 一份。`AudioDirector`
本身拿的就是 `main.ts` 的 `rng.fork()`,**多加一次 fork 不会影响世界生成**。

**这一层是这一轮信心最低的一个旋钮**——量给大了会变嘶嘶声。如果人类觉得吵,
`engineNoiseMaxGain` 调 0 就完全关掉,不牵连其他任何东西。

### 撞墙音:噪声升主角,车身层加下滑音,并且各走各的频段

第三十七节点出了两条(方波空心、主次颠倒),动手时**查出第三条,而且它大概
是"闷"最直接的原因**:

- **噪声层被低通砍掉了脆的那一半(新发现)。** 上一版 `noiseFilter` 用的是
  `lowpass`,截止频率跟车身层共用同一个 `brightness`(最高 2400Hz)——硬物
  相撞那一下 crack 的高频全被滤掉了,剩下的只有低频轰隆。现在噪声独立走
  **`highpass`**(700~2400Hz 随强度走),把低频轰隆滤掉留下脆的部分;车身层
  继续走 `lowpass` 保留重量感。**两层各管各的频段**,不再互相打架。
- **主次颠倒 → 两个增益对调。** `impactGain` 0.5 → 0.3,`impactNoiseGain`
  0.35 → 0.62。时长也对调了方向:噪声 0.045~0.12s 比车身 0.075~0.17s 更短
  (车身层也整体缩短了,原来是 0.1~0.22s,拖长了会变回"闷响的球")。
- **方波空心 → 锯齿波 + 快速下滑音。** 方波只有奇次谐波,音色学上就是空心
  音色的来源。换 `sawtooth` 补上偶次谐波;音高区间 42~85Hz 抬到 74~155Hz;
  另外加了一段自 `×3.2` 起点滑到落点的快速下滑(占总时长 35%),这是打击乐
  合成的通用做法——定频振荡器听起来是"一个音",有下滑才像"一下撞击"。

### 测试

`tests/unit/audio.test.ts`:280 → 288(+8)。除了跟着新参数改断言,还顺手修了
一个**测试本身的脆弱性**:旧的"四个维度"那条测试硬编码 `gains[0]`/`gains[2]`
的创建下标来区分两层,这一轮两层的创建顺序一调换,它会静默地断言错对象而不是
报错。换成 `capturePlay()` 顺着节点图走——先按滤波器类型(highpass / lowpass)
认出两层,再从各自的 `connected[0]` 取 gain,和创建顺序无关。

新增的断言里有几条是直接把这一轮的结论钉死的:噪声峰值必须高于车身层、噪声
衰减必须快于车身层、噪声必须走高通、车身必须是锯齿波且有下滑、音域必须
≥ 2.5 个八度、引擎只能有一个振荡器。

三道门:`typecheck` 0 错误,`test -- --run` 288 passed,`build` 通过。

**没跑 `test:visual`/`shoot`,这次是有理由的**:`?test=1` 下根本不构造

## 第三十九节:引擎补变速箱 + 碰撞分型(2026-08)

### 起因:第三十八节推上去之后人类实听的第二轮反馈

两条,都是**机制缺失**,不是音色偏好:

- 「引擎是不是应该有换挡的声音,我没听到,感觉有点假」
- 「碰撞还是一如既往垃圾,碰撞是分为好几种的,可能是摩擦过去的,可能直接
  撞过去的,而不是只是一种声音」

### 引擎:转速曲线原来是单调的,那是无级变速

第三十八节把音域拉到三个八度、把拍频源删掉,但转速代理仍然**随车速单调
上升**——物理上这就是一台无级变速的电动机。真车加速时转速是**锯齿形**的:
挡内爬升 → 升挡瞬间掉下来 → 再爬。缺了这个锯齿,音色调得再准也是"假"。

`EngineSound` 里加了 `gearRpm01()`:六个挡(`engineUpshiftPoints`,间距越往后
越宽,和真实变速箱高挡齿比更密一致),升挡后转速掉到 `engineShiftDownRpm`
(0.42,真车大约掉到红线的 40~50%)。另外两件必须一起做的:

- **降挡回滞**(`engineDownshiftHysteresis` 0.92)。升降挡共用一个阈值的话,
  车速卡在换挡点附近巡航会每帧来回换挡,听感是机关枪。单测钉了这条。
- **换挡断油**(`engineShiftCutTime` 0.12s / `engineShiftCutGain` 0.45)。
  只掉转速不切音量的话,听起来像松了一下油门,不像换挡。

**物理层没有变速箱,这一轮也没给它加。** 驱动力矩/极速/加速度一个没动
(`driveTorque` 是 CLAUDE.md 里为保甩尾手感刻意不动的),挡位纯粹是音频层
读 `speed01` 之后自己算的显示层结构,不回写任何物理量。

数值核过(满油门扫车速,`speed01 → 频率`):一挡 155→344Hz,升挡掉到 250Hz,
往后每挡都是掉约 100Hz(接近一个五度)再爬回 ~355Hz,全程 5 次升挡。锯齿是
真的存在的,不是靠单测方向性断言蒙的。

### 碰撞:根因在数据层,音频层原来分不出来也怪不着它

`Vehicle.wallImpact = min(1, 法向/总速) × 法向`——**「多硬」和「什么角度」
被乘死在同一个标量里**。音频层只拿到这一个数,不管怎么映射都还原不出两个
维度,所以只能出一种声音。这不是音频层没努力,是它没有可用的输入。

`vehicle.ts` 新增两个**纯输出**字段(不参与任何物理解算,`wallImpact` 原样
保留,`grip.test.ts` 不受影响):

- `wallNormalSpeed` —— 垂直撞进墙里的那一半(m/s)。
- `wallTangentSpeed` —— 沿墙面蹭过去的那一半(m/s)。**在「接触但没撞进去」
  的那一帧也非零**——贴着墙滑行时法向接近 0,老代码在那里直接提前返回了,
  而那恰恰是刮擦声唯一需要的信号。所以切向的赋值放在法向提前返回**之前**。

切向速度用 `velocity · (tangentX, tangentZ)` 直接点乘算,不新增临时向量,
守住每帧不分配的约定。

音频层随之拆成两条独立的路:

- **`ImpactPlayer`(事件)** 改吃两个量。`strength = 法向 / impactRefNormalSpeed`
  管多硬;`headOn = 法向/(法向+切向)` 管性格(0=纯擦过,1=纯正面撞)。四个
  `impactGraze*Scale` 让擦过去变成「薄、高、亮、短、几乎没有车身肉」,正面撞
  保持「低、沉、有肉、拖得久」。同样的法向速度,不同角度出来的是**两种音色**。
- **`ScrapeNoise`(状态,新文件 `src/audio/scrape.ts`)** 贴着墙磨多久响多久。
  高 Q 带通(`scrapeQ` 5.5)做金属摩擦的共鸣,和 `wind.ts` 的宽频低通刻意
  区分开,两层噪声不做音色区分会糊成一片;平滑常数远快于气流(0.03 vs 0.12),
  接触是通断式的,拖尾会让刮擦声黏在车后面跟着跑。

于是:正面撞进去只出 crack,贴着墙磨过去只出刮擦,斜着撞两个都有。

`AudioDirector` 现在四个消费者各 `rng.fork()` 一份。

听感/操作反馈。这一节按做的顺序记三块。

### 一、M7 名次系统(`src/game/standings.ts`)

M7 四格里碰撞已完成(第三十六、三十七节),剩 AI 竞速逻辑、赛制、HUD 名次。
先做名次,因为**另外两格都建在它上面**,而且它是纯逻辑、能单测钉死、还能
直接显示在 HUD 上用截图验证。

两个设计决定都有具体理由:

- **增量累加,不用 `laps × 圈长 + arc`。** 后者在跨起跑线的一两帧必然对不齐
  (`arc` 已经绕回 0,`laps` 要等检查点 0 判定通过才 +1),总距离会凭空少一
  整圈,名次当场翻转再翻回来。增量法只看 `arc` 的帧间变化量,超过半圈就补一个
  圈长,根本不需要 `laps`。前提是单帧位移小于半圈——60Hz 下 250km/h 也只跑
  1.2 米,余量三个数量级,这条前提写进了测试。
- **用弧长不用检查点。** `Race.progress` 按检查点算是为了防抄近道刷圈,分辨率
  太粗,同一个检查点区间内两辆车会一直并列。名次要的是空间上谁在前面,必须连续。

**发车位那个坑是拿截图快照核对时发现的,不是推演出来的。** 第一版累计值从 0
起算,等于量「自己跑了多远」。对手在玩家后面 20 米发车,两车各跑 14.5 米之后
累计值几乎相等,快照里 `position` 显示成 2——可赛道上明明是玩家领先。**跑过的
路程不等于赛道上的位置**,只要发车位不在同一点,前者就不能拿来排名次。改成
累计值的起点 = 发车位相对起跑线的**带符号**弧长(线后 20 米是 −20,不是
`圈长−20`,后者会被当成领先一整圈)。修完快照是 `position:1 / player 14.48 /
rival −3.41`,对上了。**这条正是 CLAUDE.md 那句「改完必须自己看画面」值钱的
地方:三道门当时全绿,只有快照数字不对。**

HUD:LAP 徽章旁加 `P几/几`(领跑时金色),计时卡加 GAP 行(米,负=领先,符号
约定和分段 delta 一致,超一公里改用 km)。没有对手的 `flat` 场地整个隐藏。

### 二、音频:开局无声是解锁逻辑的真 bug

人类反馈「刚开始游戏没有声音,要撞一下车之后才有引擎声」。查出来是两处:

- `AudioBus.resume()` 写的是 `if (state === 'suspended') resume()`。**Chrome
  的自动播放策略下,未经手势创建的 `AudioContext` 可以报告 `state ===
  'running'` 却根本不出声**——被策略挡住和被 `suspend()` 挂起是两回事,`state`
  只反映后者。这个 if 把唯一能解锁它的调用跳过了。改成无条件调。
- `main.ts` 原来是首次按键/点击就把监听器摘掉(`resumeAudioOnce`)。`resume()`
  是异步的且第一次未必成功,一旦没生效后面就再没人调了。改成每次手势都调,
  直到 `isRunning` 为真才摘;菜单「开始」按钮也显式调一次,不指望冒泡。

**撞击音「还是很糟糕」——这次没有猜,量了。** 4 个 seed × 4 种转向偏置各跑
60 秒,统计真实撞墙帧:

```
法向 m/s: p50=0.12  p90=0.16  p99=2.97  max=33.14
headOn:   p50=0.272(大多数接触是擦的,不是正面撞的)
```

两条结论,都直接改了参数:

1. 老的 `impactRefNormalSpeed=12` 是照着「43km/h 垂直撞墙」定的,而**99% 的
   撞击法向速度不到 3 m/s**,全被压在强度 0.05~0.25 的底部——每次都又轻又薄
   又短。参考值降到 6,同样一下撞击强度翻两到四倍;峰值音量也提到能盖过引擎
   (0.16)和气流(0.14)。
2. **90% 的「接触帧」法向速度不到 0.16 m/s**——那是贴着墙磨。阈值卡在
   0.6 m/s,并新增 **0.12 秒重触发冷却**:不挡的话磨墙时法向速度在阈值上下抖,
   每几帧放一次 crack 连成机关枪,比「太闷」还难听。持续接触已经由
   `ScrapeNoise` 负责。窗口内强度超上一次 1.6 倍仍可打断,免得真撞重了被前一下
   轻碰吃掉。

量的办法值得记下来:把 `wallNormalSpeed`/`wallTangentSpeed` 暴露到测试快照,
然后在 **vitest 里**直接跑 `Vehicle` + `Autopilot`(Rapier 在 Node 里跑得起来,
见 CLAUDE.md 的无头验证契约),4.5 秒出结果,不用开浏览器。

### 三、鼠标自由视角(`src/core/mouseLook.ts`)

人类要「通过移动鼠标动视角,和正常游戏一样那种」。

用**指针锁定**而不是读光标坐标:光标会被窗口边缘卡住,转到一半就转不动了。
点画面进锁定,Esc 退出(Esc 同时是暂停键,松鼠标的同时把游戏停下是符合直觉的)。

相机实现是**绕着车转**,不是原地转头:把「相机相对车的偏移向量」先绕世界 Y 轴
转偏航、再绕转完之后的水平右轴转俯仰。原地转头看到的是空地,那不是第三人称
环视。同时一旦开始环视,注视点从「车前方的路」平滑挪到「车本身」,否则镜头绕到
侧面时车会滑出画面。停手 1.1 秒后自动回正——不回正的话视角很容易落在侧面然后
忘了摆回来,车就没法开了。

俯仰符号写反过一次(正俯仰把相机压进了地面,被 `minGroundClearance` 夹住),
是单测抓到的:`抬高俯仰会把相机抬起来` 那条直接红了。

**测试模式不构造 `MouseLook`**,`?test=1` 下没有任何监听器能改相机,「同 seed
同输入逐帧复现」的契约不受影响;单测里另有一条断言「不动鼠标时相机位姿和没有
这个功能时逐位一致」。

验证:临时在测试模式里把视角角度写死成 (1.15, 0.45) 拍了一张,确认相机绕到
侧上方、车仍然居中,然后把临时改动撤掉。

## 第四十一节:M7 竞速 AI + 「能不能一直开到极速」这个问题的答案(2026-08)

### 一、AI 车太慢:先量,再改

人类说「AI 车太垃圾了,就是说特别慢也不聪明」。量了一遍,五条精选赛道:

```
seed 135  目标 72.0s   Autopilot 123.3s(+71%)  均速 91km/h  满油门占比 5%
seed 325  目标 72.6s   Autopilot 126.1s(+74%)  均速 85km/h  满油门占比 5%
seed 107  目标 72.4s   Autopilot 123.6s(+71%)  均速 88km/h  满油门占比 5%
seed 110  目标 70.5s   Autopilot 118.0s(+67%)  均速 92km/h  满油门占比 6%
seed 154  目标 74.5s   Autopilot 115.9s(+56%)  均速 91km/h  满油门占比 8%
```

**满油门占比只有 5%** —— 这就是全部原因。`Autopilot` 的逻辑是「前方判定为弯
→ 油门归零 + 空气刹拉满」,而「是不是弯」的阈值很低,于是整圈几乎都在滑行。
它从来不问「这个弯到底能多快过」。

**新增 `src/game/racingPilot.ts`,`Autopilot` 一个字没动。** 后者是 M2 留下的
验收工具(自己的注释写着「不是游戏内容」),截图回归的既有基线全靠它逐帧
稳定,改它等于把整套视觉基线一起动了。

新 AI 三步,都是实车赛道工程的标准做法:

1. **弯速上限由曲率反解**:`v = √(a_lat · R)`,`R = 1/κ`。曲率用一段基线上的
   切线转角除以弧长算,比逐点差分抗噪。
2. **刹车点由弯速反解**:朝前扫 260 米,对每个采样点算「要在那里降到 v_j,
   现在最多能多快」= `√(v_j² + 2·a_brake·d)`,取最小值。这一步就是「提前
   减速」的全部内容——不需要判断「是不是弯」,直接得到当前允许的最高速度。
3. **油门/刹车分三档**:低于目标给油、高于目标刹车、中间留一条滑行带,免得
   在目标速度附近油门刹车来回抖。

另外走线朝弯内偏(`lineOffset` 0.62):沿中心线跑等于把弯道半径用满了却一米
不占便宜,往内切能撑大有效半径,弯速上限跟着涨。

结果:

```
aggression 0.70   +9%   −8%   −2%   −4%  −11%   (全程 0 撞墙)
aggression 0.85   +2%  −14%  −11%  −13%  −18%
aggression 1.00   −6%  −18%  −20%  −16%  −23%
```

**AI 全力跑比目标时间快 6~23%,而且一次墙都不撞。** 默认压到 0.7 不是因为它
做不到,是因为一个永远领先两成的对手不好玩——这是玩法取舍,写在
`RACING_AI.defaultAggression` 的注释里,以后做难度档直接调这个数(1.0 已经
验证过跑得完)。

避让只做了最基本的一条:正前方近距离且横向也近的车 → 侧移 + 收油,不追尾。
超车靠速度差自然发生。刻意的博弈要等赛制做完。

### 二、「真车能一直开到极速吗、这么快过弯不会出问题吗」

两个问题,答案不一样,**一个不是 bug,一个已经是对的**。

**(a) 一直保持极速——不是 bug,而且正好是照着现实建的。**

查了实现:`vehicle.ts` 里极速由 `maxSpin = REFERENCE_TOP_SPEED × 1.15`
(= 69.3 m/s = 250 km/h)这个**轮速硬钳位**决定,不是气动阻力平衡决定的。
`CAR.dragArea = 0.7` 单独作用的话极速会落在 300 km/h 出头,所以钳位才是
生效的那个。

而这**正是在模拟 A110 的电子限速**——CLAUDE.md「现实参照」那节写得很清楚:
参照车官方数据是「0-100 km/h 4.5s、**电子限速极速 250 km/h**」。带限速器的
真车在直道上就是这个行为:顶到限速器,然后纹丝不动。所以「保持不变」是对的。

至于过热:**ICE 赛车在一圈之内基本不会因为热衰减掉极速**,那更多是电车和
民用车的现象;真赛车一个圈里衰减的是**轮胎和刹车**,不是极速。真要加,该加的
是轮胎衰减/刹车热衰,而不是给极速加个温度上限——后者对这台参照车反而更不真实。
这是个玩法范围问题(而且 CLAUDE.md 的「不做的事」里没有它),留给人类决定。

**(b) 高速过弯会不会出问题——已经会出问题了,这条已经是对的。**

量了「强制全油门不许收、跑 60 秒」:

```
seed 135  半宽 7.5m   最大横向偏移 13.6m   撞墙 35 帧   速度区间 27~248 km/h
seed 107  半宽 7.5m   最大横向偏移  7.2m   撞墙  0 帧   速度区间 47~248 km/h
```

seed 135 那条直接被推出赛道 13.6 米(半宽只有 7.5 米)并且撞墙。也就是说
**这台车过弯已经有速度代价了**,和 CLAUDE.md「过弯要有速度代价,不做怎么开都
能拽回来的街机手感」一致。人类观感上「高速过弯没事」,更可能是因为之前的对手
AI 全程在滑行(满油门 5%),看不出代价。

### 三、量的办法

两轮都是在 **vitest 里直接跑 `Vehicle` + 车手**(Rapier 的 wasm 在 Node 里
跑得起来,而且和浏览器逐位一致,见 CLAUDE.md 的无头验证契约),3~7 秒出结果,
不用开浏览器。需要什么中间量就先暴露到 `Vehicle` 的只读字段或测试快照上——
这一节用到的 `wallNormalSpeed` 就是上一节为音频加的,正好复用。

`test:visual` 19 项全绿。

完全一致」那条——当初 `RIVAL_START_GAP = 20` 米的纵向错开留的余量够用。

## 第四十二节:M7 收官 —— 对手出界回收 + 赛制(2026-08)

人类看完第四十一节的进度汇报后说「OK来吧」,按汇报里排的优先级做了两件事。

### 一、对手车出界回不来(确认的 bug,已修)

出界重置逻辑原本长在 `Race` 里,而 `Race` 是**玩家专属**的(它还管圈速、
分段 delta、纪录持久化),`World` 只把玩家传给 `race.update()`。于是对手车
被撞出赛道之后没有任何东西会把它拉回来 —— 永远躺在山坡上,而名次表还在
认真统计它。

拆出 `src/game/trackRecovery.ts`,每辆车各持一份:

- `Race` 改为委托给它,`offTrackTime`/`resets` 变成只读转发,宽限时间与判定
  条件逐字搬过来,**玩家行为不变**(既有测试全绿)。
- `World` 给对手车挂一份。玩家送回「最近通过的检查点」(不许靠出界抄近道),
  对手送回「它自己当前的弧长」—— AI 不刷成绩,原地扶起来就行,送回检查点
  反而是平白惩罚。

**写测试时踩到一个真坑,记在测试注释里**:把车挪出赛道**必须走
`vehicle.reset()`**,直接改 `vehicle.position` 下一帧就会被 `readState()`
用 Rapier 刚体的旧变换覆盖掉,车压根没离开过赛道 —— 第一版测试就是这么
假绿的(断言"出界了"却一直是 false)。位置的权威在刚体上,不在那个字段上。

### 二、赛制(M7 最后一格)

`src/game/raceSession.ts`,三个阶段:

- `countdown` —— 3 秒发车倒计时,**期间输入被锁死**(玩家和对手都锁)。
  抢跑不判罚,是压根动不了 —— 比事后罚时直观。锁的是写进物理的那份输入,
  不改调用方的帧。
- `running` —— 跑满 `RACE_FORMAT.lapCount`(3 圈)就记一次完赛。
- `finished` —— 所有车完赛,**或者**冠军冲线之后又过了 20 秒宽限。没有这条
  宽限的话,一辆被撞出赛道慢慢爬回来的车能让结算画面一直等下去;强制结算时
  没冲线的车按当时名次补进结果并记 DNF,**不能从结算画面里凭空消失**。

**完赛判定读 `Standings.laps` 而不是 `Race.laps`**:`Race` 只伺候玩家,
而 `Standings` 的圈数是从弧长增量累计推出来的,每辆车都有,跨起跑线也不会
抖(见第四十节)。名次顺序也现成 —— 按 `standings.order` 遍历,同一帧多车
完赛时冲线顺序才和名次一致。

**测试模式跳过倒计时**(`World` 构造时传 `skipCountdown: testMode`):截图
回路要逐帧确定,不能让前 180 帧全耗在倒计时上 —— 既有冒烟测试从第 60 帧就
开始断言车在动。真人游戏走开始菜单,倒计时在那之后,两条路径天然一致。

HUD:圈数徽章变成 `LAP 1/3`(冲线后停在 `3/3`,不会出现 `4/3`)、画面中央
的倒计时大字、结算面板(冠军金色,DNF 显示 DNF)。

## 第四十三节:把「范围决策」那批全做了(2026-08)

人类看完第四十一节的现实差距对照之后说「这些要」,把原本列为范围决策的
六项全部纳入。按做的顺序记,每一块都单独过了四道门再提交。

### 一、多辆对手 + 难度拉到收益拐点

`World` 从单数 `rival` 重构成数组。发车格取代原来「沿赛道往回退 20 米」的
一字纵队 —— 多辆车用纵队会全叠在同一条线上互相追尾。杆位(玩家)留在中心线
上,理由写在 `gridSlot()` 里:摆偏之后玩家一上来就得先并回中间,而且
「起跑在中心线」是既有截图测试钉住的行为(`|lateral| < 1`)。

**顺带修了一个真 bug**:`RacingPilot` 构造函数把 `aggression` 钳在
`[0.3, 1]`,于是传任何大于 1 的值都没有效果 —— 第一次扫 1.15/1.30/1.45 时
五条赛道数字**一模一样**,就是这个钳位吃掉的。上限放到 2 之后重新标定,
1.4 是收益拐点(1.8 再快只换来零点几个百分点,seed 135 反而倒退)。每辆
对手再递减 0.12,全场同速会变成一列火车。

### 二、按车辆状态补声音

`Vehicle.gripSaturation` 的注释从一开始就写着「给音效和 HUD 用」,但音频层
一直没接过它 —— **甩尾是这个游戏的核心机制,却一直是静音的**。补了三样:
轮胎尖叫(高 Q 带通,抓地饱和 + 真的滑出速度**两个条件都要满足**)、出界
地面噪声(低通 380Hz,出界要「变粗糙」不是「变吵」)、落地闷响。

### 三、尾流

`src/game/draft.ts`。实测满尾流(减阻 35%)从 120 km/h 全油门 5 秒多走
2.1 米,从 180 km/h 起只多走 1.2 米 —— **越快收益越小**,和「阻力随 v² 涨」
的直觉相反。原因是极速由 `maxSpin` 轮速硬钳位决定(模拟 A110 的 250 km/h
电子限速),不是阻力与推力的平衡:接近限速时省下的阻力没地方去。真实的带
限速器的车也是这样。

单测抓到一个浮点陷阱:判定用「前车相对车头方向的投影」,而正侧方(90°)的车
投影是 `距离 × cos(90°)`,浮点下 `Math.cos(Math.PI/2)` 是 6.1e-17 不是 0,
于是投影是极小的**正数**,会被判成「正前方贴着」拿满额减阻。加了纵向下限。

### 四、轮胎磨损 / 刹车热衰 / 碰撞损伤

`src/game/condition.ts`。三样都是**从 0 开始**的累积量,所以一局刚开始的车
和加这套系统之前逐位一样 —— 已验收的手感基线(峰值侧向 1.3~1.6 g、甩尾稳态
侧滑角)是在新胎冷刹的车上验的,不受影响。

磨损跟「滑移功率」(抓地饱和度 × 车速)走,不跟时间走:贴着极限开磨得快 ——
这是真实轮胎管理的核心,会开的人能让胎多撑几圈。损伤**不可修复**,
`vehicle.reset()`(出界回收)不清车况:把车扶回赛道是回收,不是修车。

**两轮标定都是量出来的,第一版两个都是废的**:

- 磨损速率 0.0016 → 跑完 3 圈只磨两成、抓地掉 3%,人根本感觉不到。改 0.0045。
- 刹车升温 0.09 / 冷却 0.055 → 跑完 3 圈刹车温度**恒为 0**。车手不是一直踩着
  刹车的,占空比撑死两成,`0.09 × 0.2` 抵不过 `0.055` 的冷却。改 0.4 / 0.05。
  真实刹车也是这个形状:升温极快,冷却很慢。

**加磨损之后量出两个卡死 AI 的 bug**:

1. `RacingPilot` 的弯速预算按新胎算,胎磨掉之后一路滑出赛道,seed 135 第 3 圈
   从 58.9s 掉到 77.3s。现在预算跟着 `tireGripScale`/`brakeScale` 缩放 ——
   真实车手感觉到胎不行了会自己收着开。
2. seed 107 的 AI 顶在护墙上**不出界地**卡死:出界判定一次都不成立(出界帧
   0、回收 0 次),车速 0 持续 230 秒 —— 只看出界的回收对这种情况完全无效,
   而 `RacingPilot` 从不挂倒挡,自己退不出来。`TrackRecovery` 加了 opt-in 的
   卡住检测(**只给 AI 开**,玩家停车是合法操作),发车倒计时期间不启用。

### 五、物理层变速箱

`src/game/gearbox.ts`。**和 `audio/engine.ts` 里那套同名的东西不是一回事** ——
那个是纯显示层的,读车速自己算挡位只为生成转速锯齿;这个决定车轮上到底有
多少力矩。模型是标准的「扭矩曲线 × 齿比 × 主减速比」,换挡期间断动力。

**这一块直接动了 CLAUDE.md 保护的手感,过程记下来**:第一版
(`idleTorque` 0.55 / `torqueScale` 0.098)把一挡的轮上力矩normalize 到和原来
的恒定力矩差不多 —— 这是错的,真实一挡会把扭矩放大得多。后果立刻被测试抓到:
**甩尾稳态侧滑角从 9.70° 塌到 1.95°**,正是 CLAUDE.md 里写明的那条耦合
(甩尾靠「驱动力矩超过后轴抓地预算」触发)。往上调到 `idleTorque` 1.0 /
`torqueScale` 0.15 之后,`grip`/`gripFlat` 的全部手感断言恢复通过。

结果对照:

```
                0-100     0-200    极速     换挡点(km/h)
恒定力矩(旧)   3.62s     6.20s    248
带变速箱(新)   3.88s     7.22s    248     61 / 108 / 152 / 200
真实 A110       4.5s       —       250(电子限速)
```

0-100 从 3.62 挪到 3.88,**方向是朝着真实的 4.5 秒走的**;极速不变(仍由
限速器决定)。**但这是改了已验收手感的改动,需要人类重新试玩确认**,
自动化测试只能保证侧滑角那条硬线没塌。

### 四道门

`typecheck` 0 错误、`test -- --run` **417 passed**(本节起点 395)、`build`
通过、`test:visual` 19 项全绿。

燃油载荷、天气/路面温度、维修进站。**载具造型**人类也提了(「还是有点像

## 第四十四节:载具造型 —— 从「玩具车」往真车挪一档(2026-08)

人类提过「汽车的模型你还没做好吧,还是有点像玩具车」。CLAUDE.md 写明造型有
硬天花板(程序化 `BufferGeometry` 做不出照片级外形),**但「玩具」和「照片级」
之间还有很大一段**,这一节做的就是那一段。

### 查出来的四条「玩具感」来源

1. **横截面只有 8 个点。** 车身是个八棱柱,无论怎么打光都是硬邦邦的多面体。
   `RING` 提到 24,并且把「直角 + 倒角」换成**超椭圆**采样(`ringPoint`):
   `chamfer` 越大越接近椭圆、越小越接近矩形,中间连续过渡。八点盒子在角上只有
   一条斜边,而超椭圆在角上有好几个点,高光能沿棱线连续滚过去 —— 那才是钣金。
2. **全部平面着色。** 提了分辨率却还 `flatShading: true`,等于白提。车身改走
   `mergeVertices` + `computeVertexNormals` 的平滑法线。
3. **座舱是一块实心 accent 色。** 从车外看,真车的座舱主要就是一整片深色玻璃。
   换成低粗糙度 + 半透明的玻璃材质,靠**反射天空**而不是靠颜色读出「玻璃」。
   顺带补了一块车顶壳 —— 玻璃半透明,不盖顶的话从上方能看穿到车里,空心的车
   比不透明的盒子更假。
4. **没有轮眉。** 平直的侧板底下探出四个轮子,像积木插了四个轮。补了贴着轮胎
   的一圈弧形翼子板边缘。

另外补了三样「人眼判断车 / 玩具」的强信号:**后视镜、前大灯、下进气口**。
玩具车通常正是省掉这些。大灯不用自发光(那是尾灯为了配合 bloom 才用的),
白天的前灯靠低粗糙度玻璃反射读出来,和座舱玻璃同一套逻辑。

逐面明度抖动(`spread`)在车身上关掉了:那是低多边形时代的补偿,面少时防止
糊成一整块;24 边的连续曲面上再抖就是一身脏斑。

### 一个只有看图才发现得了的错

第一版轮眉的圆心写死在 `y = 0`(车身局部原点),而静止时轮心在
`wheelRadius − suspensionRest = −0.11`,加上半径给到 1.28 倍轮半径 ——
截图里就是**四个悬在车头车尾的大黑箍**,比改之前还难看。几何本身没有任何
不合法的地方,`typecheck`/`test` 全绿,单测也不可能发现。改成
`ARCH_Y = CAR.wheelRadius - CAR.suspensionRest`、半径压到 1.13 倍、再往车身里
埋 7 厘米之后才对。**这就是 CLAUDE.md「改完必须自己看画面」那条规矩的价值。**

### 代价与验证

三角形数量涨约三倍(车身 ~1100 面),四辆车四千多面 —— 相对地形和赛道条带
低一个数量级,`test:visual` 的帧时间检查照常通过。

四道门:`typecheck` 0 错误、`test -- --run` **417 passed**(无变化,造型没有
单测覆盖)、`build` 通过、`test:visual` 19 项全绿。侧视/前视截图都亲眼看过。

**仍然是需要人类看图确认的东西**(M3 视觉基线归人判断),而且**天花板没有变**:
造型仍然做不到实拍级,这一节只是把「玩具」挪到了「能一眼认出是车」。

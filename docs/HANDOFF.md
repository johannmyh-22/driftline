## 二、三条不可动摇的约束

来自 `CLAUDE.md`,违反了就是方向性错误:

1. **零二进制资产。** 仓库里只能有文本文件。贴图运行时程序化生成到 `DataTexture`,
   音效用 Web Audio 合成。**写实和零资产不冲突** —— 沥青、沙地、混凝土护墙、
   法线贴图全是运行时算出来的。
2. **改完必须自己看画面。** 跑 `npm run shoot`,然后用 Read 工具**真的打开那张 PNG**。
   编译通过 ≠ 画面正确。见第五节,这个项目在这上面栽过很多次。
3. **一个里程碑一个 PR。** 不要顺手做下一个里程碑的事。

### 视觉方向(2026-08 由人类改定)

原定的「低多边形」**已作废**,改为尽量接近实拍照片。天花板写在 `CLAUDE.md`:

- **能做到接近实拍**:光照、大气散射、PBR 材质、色调映射、后处理。
- **做不到实拍级**:复杂**造型**。手写 `BufferGeometry` 出不了照片级的载具外形。
  人类已经指出过「车子太假」,并且明确这不是当前阶段的事 —— **材质可以继续救,
  造型不要硬碰**。

## 三、代码地图

```
src/core/     引擎无关:定步长主循环、seeded PRNG、输入层、数学工具、测试接口
src/game/     玩法:载具物理、赛道生成与查询、相机、计时、数值
src/gfx/      渲染:大气、贴图生成、各种网格、后处理链、配色
scripts/      截图与性能脚手架
tests/unit/   逻辑测试(180 条)
tests/visual/ Playwright 截图冒烟(13 条)
```

### 几个关键文件

- **`src/game/tuning.ts`** — 所有手感与视觉数值的唯一来源,分 `VEHICLE` / `CAMERA` /
  `TRACK` / `SKY` / `CRAFT` / `POST` 六段。**人类调手感只改这一个文件。**
  每个值都写了「为什么是这个数」,好几处还写了「改这个必须回头核哪个」。
- **`src/game/course.ts`** — 赛道的两段式地面查询。**全项目最重要的不变量所在。**
- **`src/game/vehicle.ts`** — 悬浮控制器。物理都在这儿,数值都不在这儿。
- **`src/gfx/postprocess.ts`** — 后处理链。顺序有硬约束,注释里写了为什么。
- **`src/gfx/atmosphere.ts`** — 大气与 IBL。里面有一道**必须存在**的辐射钳制。
- **`src/gfx/textures.ts`** — 程序化 PBR 贴图生成器。

## 四、必须理解的不变量

破坏它们不会立刻报错,但会让整个项目慢慢烂掉。

### 1. 物理查询的面 == 渲染出来的面

`Course` 预先算好一张条带顶点网格,**渲染网格和 `sample()` 吃同一张表、同一套
三角划分**。`tests/unit/course.test.ts` 拿 600 个三角形重心直接断言这一点。

**推论:同一条边只能有一个高度。** 护墙也必须坐在条带自己的外缘顶点上
(`Course.buildEdgeLine()`)。老版护栏照着 `sample.y` 和 `bank` 另算了一套高度、
还带一个 0.5 的经验系数,结果墙底和路肩对不上,远看就是一条浮在地上的带子。

赛道外的地形是例外(噪声高度 + 有限差分法线),那里是出界区。

### 2. 同一个 seed 必须逐帧复现

- `src/` 下**禁止 `Math.random()`**,`tests/unit/noMathRandom.test.ts` 会扫描拦截。
- 所有随机走注入的 `Rng`(mulberry32),用 `fork()` 派生子流。
- 主循环是定步长累加器,`?test=1` 时**完全不注册 rAF**,只由 `advance(n)` 推进。
- `InputRecorder.record()` 会**就地**把实时输入量化成回放精度。

### 3. 截图回路是这个项目的地基

CI 没有 GPU,WebGL 走 SwiftShader。`npm run shoot` + `tests/visual/smoke.spec.ts`
是 agent **唯一能看见画面**的途径。

**性能预算(实测,1280×720,chase 机位):**

| 配置 | 每帧 |
|---|---|
| 无后处理 | 325 ms |
| 仅 composer(RenderPass + OutputPass) | 347 ms |
| 默认链(bloom + SMAA + 暗角) | 621 ms |

冒烟测试全套约 **116 秒**(M0 时是 27.7 秒)。**这条回路挂了就等于瞎着写代码,
变得太慢要先停下来解决,不要硬推。**

## 五、这个项目吃过的亏

按「只有看图才能发现」的程度排序。前四条是历史,**第 5、6 条是 M3 这轮的,
而且是同一类**。

1. **转向左右反了。** 单测断言的是「yaw 与 steer 同号」,而 yaw 正方向到底是左是右
   *正是搞反的那件事* —— 断言和 bug 共用同一个错误前提,83 条测试全绿也拦不住。
   **教训:断言物理位置,不要断言内部约定的符号。**
2. **烘环境贴图时天空整个变黑。** `scene.add(sky)` 会把天空从世界场景摘走。
3. **地形三角形压在赛道上。** 剔除只按重心判断。
4. **贴地阴影不出现。** 扇形三角的绕序反了,整个面朝下被背面剔除。
   护墙现在按左右侧分绕序,`tests/unit/trackMesh.test.ts` 拿三角形**自己的叉乘**
   和着色法线做断言 —— 那条测试验证过:故意改回同一套绕序,它报 -0.9999。
5. **车漆反射成磨砂玻璃。** metalness 高了之后基色只决定反射色调,车身没有自己的
   颜色。**同一个坑踩了两次**:第一次修了 hull,漏了 fin,直到人类看图才发现
   侧翼是块比尾焰还亮的白斑。

### 6. 两次 NaN 黑屏 —— 这一类最难认,务必读完

两次都是 **HDR 值溢出成 Inf/NaN,再被某个模糊/卷积核摊到一大片**:

- **bloom**:天空冲破 `HalfFloatType` 的 65504,高通之后被 mip 链一摊,整屏变黑。
- **天空辐射污染 IBL**:Preetham 在太阳附近能算到上千(shader 里 `EE = 1000`),
  烘 PMREM 时溢出,**整张环境贴图变 NaN,所有 PBR 材质一起变黑**。表现是
  「天空正常、地面纯黑剪影」,看着像地形没被照亮。太阳仰角一过 15 度就触发。

两处钳制现在分别在 `gfx/postprocess.ts` 的 `clampBloomInput()` 和
`gfx/atmosphere.ts` 的 `clampSkyRadiance()`,**都不能删**。

**NaN 有传染性,这是它难认的根源**:把 `bloomStrength` 或 `environmentIntensity`
调成 0 也照样黑,因为 `0 * NaN` 还是 NaN。所以「关掉某个效果看看」这个惯用的
排查手段在这里会给出错误结论。

**而它们差点漏过去的原因,比 bug 本身更值得记住:**

- **`npm run shoot` 的默认 seed 是 42,而 42 恰好是两个 bug 都幸免的少数 seed 之一。**
  所有回归截图都是好的,只有实时模式(默认 seed 1337)是黑的。
  **换 seed 复核,不要只信默认那一张。**
- **既有的冒烟断言结构性地拦不住这类问题。** 「换 seed 会换掉地形与配色」断言的是
  两个 seed 之间平均色差够大 —— 而一张正常图和一张全黑图之间的色差**更大**,
  断言反而更容易通过。方差同理:天空正常而地面归零时,画面对比度更高、方差更大。
  现在补了 `lowerMeanLuminance`(画面下半幅平均亮度),逐个 seed、两头都卡。

### 两个测量方法的坑

- **别拿速度差反推侧向加速度。** 车头转动本身会让机体系下的侧向速度以 ω·v 变化。
  `Vehicle.lateralGripAccel` 直接暴露抓地力实际施加的加速度。
- **测试失败时先找真实原因,别急着放宽容差。** 左右镜像那条差了 0.04°,看着像浮点
  噪声,实际是出生点压平区不够长。放宽容差会把真实原因永久盖掉。
  M3 这轮又遇到一次:空中回正那条从「侧滑角绝对变化 < 5°」改成了「侧滑角**没有向
  0 收敛**」—— 后者才是回正力矩真正的特征,前者的容差会跟着手感数值一起漂。

## 六、当前手感数值(实测)

改 `tuning.ts` 之后这些会变,`tests/unit/vehicle.test.ts` 和 `grip.test.ts` 里的
区间就是它们的规格书 —— **测试挂了不一定是 bug,但一定意味着手感变了,需要人类确认。**

| 项目 | 值 |
|---|---|
| 0 → 100 km/h | **2.3 s**(人类反馈 0.92 s「太快、不写实」后放慢) |
| 极速 | 315 km/h |
| 峰值侧向抓地加速度 | 3.80 g |
| 满舵侧滑角峰值 | 57°(甩尾,不是打转) |
| 赛道长度 | 2.8–3.4 km,10 个 seed 全部可跑完 |

**两条关键设计:**

- **偏航角速度上限由可用侧向力推出(ω = a_lat / v),外加侧滑回正力矩。**
  少了任何一个,车都会一打方向就原地打转。
- **恒定推力下,起步加速度和极速是绑死的。** `a(0) = thrust`,极速由推力与阻力的
  平衡点决定。所以放慢起步必须同步降阻力,否则极速一起掉(实测 thrust 34 → 13
  会让极速掉到 154 km/h)。降的是**线性项**(0.18 → 0.05)—— 那是轮胎滚阻的量级,
  而这台车没有轮胎。代价是松油门滑行更久,那反而更贴合设定。

## 七、后处理链的取舍(有数据支撑,别凭感觉改)

`RenderPass → bloom → OutputPass → SMAA → 暗角`。顺序有硬约束,排错了不报错、
只让画面悄悄变糟 —— 理由写在 `postprocess.ts` 的类注释里。

**AO 实现了但默认不启用**,这是量出来的决定:

| 环节 | 每帧成本 | 画面差异 |
|---|---|---|
| 暗角 | +45 ms | 明显 |
| bloom | +155 ms | 明显 |
| SMAA | +178 ms | 明显 |
| **AO** | +169 ms | **平均 3.8/255,肉眼看不出** |

AO 弱不是配置错了:开阔沙漠、平坦赛道,**而且反重力载具悬浮在地面 1.6 米以上,
连接触点都没有**。半径从 0.45 米加到 2.5 米差异反而更小。M5 的隧道段进来之后,
把 `'ao'` 加回 `DEFAULT_STAGES` 即可。

### bloom 阈值:一个数不能同时服务两个目标

阈值既要**压住整片天空**(否则逆光时全屏发白),又要**放行尾焰**(否则速度感没了)。
上一版为了救逆光把它从 3.5 提到 8,却没同步抬尾焰亮度 —— 尾焰当时是 6.2,正好掉到
阈值以下,辉光整个消失,**是人类试玩才发现的**。

现在两边分开:阈值留在 8 压天空,尾焰亮度(`CRAFT.thrusterFullGain`)抬到约 15。
两处注释互相点名。**改任何一边都要回头核另一边。**

## 八、工作方式

- **分支**:harness 每轮指定固定分支。**PR 合并后必须从 `origin/main` 重开同名分支**,
  不能往已合并的历史上继续堆提交。
- **提交前必过**:`npm run typecheck` / `npm run test -- --run` / `npm run build` /
  `npm run test:visual`。
- **人类的反馈风格**:给的是现象(「车太飘」「视角偏得离谱」「眼睛要瞎掉」),
  需要自己去测量、定位根因。他会验收手感和画面,**这两件事不要自己下结论**。
- **额度有限**,他会喊停。停的时候确保工作已提交推送。

### 常用命令

```bash
npm run dev                                     # 本地开发
npm run shoot                                   # 截图(默认 chase 机位、seed 42)
npm run shoot -- --camera=side --throttle=0     # 静止侧视,看载具本身
npm run shoot -- --seed=99 --frames=420         # 换 seed / 跑到赛道深处
npm run shoot -- --extra=post=none              # 关掉后处理做对比
npm run shoot -- --no-build                     # 复用现有 dist,连拍时省时间
npm run perf                                    # 量每帧渲染成本
```

机位:`chase` / `side` / `front` / `top` / `map`。
`?course=flat` 切回 M1 那块平地,`?post=none` 关掉整条后处理链。

**`npm run perf` 为什么必须存在**:`shoot` 和冒烟测试的墙钟时间**量不出**每帧成本 ——
`Loop.advance(n)` 走 n 个物理步之后只渲染一帧,那两个数字里绝大部分是构建、
启动和场景生成。perf 改成逐帧 `advance(1)`,再用一次截图强制结算 GL 队列。
(顺带一提:页面内的 `performance.now()` 也量不准,它只看到命令提交的时间 ——
实测 0.4 ms/帧,而墙钟是 325 ms/帧。)

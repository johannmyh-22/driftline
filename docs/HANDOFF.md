## 二、三条不可动摇的约束

来自 `CLAUDE.md`,违反了就是方向性错误:

1. **零二进制资产。** 仓库里只能有文本文件。贴图运行时程序化生成到 `DataTexture`,
   音效用 Web Audio 合成。**写实和零资产不冲突** —— 沥青、沙地、混凝土护墙、
   法线贴图全是运行时算出来的。
2. **改完必须自己看画面。** 跑 `npm run shoot`,然后用 Read 工具**真的打开那张 PNG**。
   编译通过 ≠ 画面正确。见第五节,这个项目在这上面栽过很多次。
3. **一个里程碑一个 PR。** 不要顺手做下一个里程碑的事。

### 视觉方向(2026-08 由人类改定)

原定的「低多边形」**已作废**,改为尽量接近实拍照片。天花板写在 `CLAUDE.md`:

- **能做到接近实拍**:光照、大气散射、PBR 材质、色调映射、后处理。
- **做不到实拍级**:复杂**造型**。手写 `BufferGeometry` 出不了照片级的载具外形。
  人类已经指出过「车子太假」,并且明确这不是当前阶段的事 —— **材质可以继续救,
  造型不要硬碰**。

## 三、代码地图

```
src/core/     引擎无关:定步长主循环、seeded PRNG、输入层、数学工具、测试接口
src/game/     玩法:载具物理、赛道生成与查询、相机、计时、数值
src/gfx/      渲染:大气、贴图生成、各种网格、后处理链、配色
scripts/      截图与性能脚手架
tests/unit/   逻辑测试(180 条)
tests/visual/ Playwright 截图冒烟(13 条)
```

### 几个关键文件

- **`src/game/tuning.ts`** — 所有手感与视觉数值的唯一来源,分 `VEHICLE` / `CAMERA` /
  `TRACK` / `SKY` / `CRAFT` / `POST` 六段。**人类调手感只改这一个文件。**
  每个值都写了「为什么是这个数」,好几处还写了「改这个必须回头核哪个」。
- **`src/game/course.ts`** — 赛道的两段式地面查询。**全项目最重要的不变量所在。**
- **`src/game/vehicle.ts`** — 悬浮控制器。物理都在这儿,数值都不在这儿。
- **`src/gfx/postprocess.ts`** — 后处理链。顺序有硬约束,注释里写了为什么。
- **`src/gfx/atmosphere.ts`** — 大气与 IBL。里面有一道**必须存在**的辐射钳制。
- **`src/gfx/textures.ts`** — 程序化 PBR 贴图生成器。

## 四、必须理解的不变量

破坏它们不会立刻报错,但会让整个项目慢慢烂掉。

### 1. 物理查询的面 == 渲染出来的面

`Course` 预先算好一张条带顶点网格,**渲染网格和 `sample()` 吃同一张表、同一套
三角划分**。`tests/unit/course.test.ts` 拿 600 个三角形重心直接断言这一点。

**推论:同一条边只能有一个高度。** 护墙也必须坐在条带自己的外缘顶点上
(`Course.buildEdgeLine()`)。老版护栏照着 `sample.y` 和 `bank` 另算了一套高度、
还带一个 0.5 的经验系数,结果墙底和路肩对不上,远看就是一条浮在地上的带子。

赛道外的地形是例外(噪声高度 + 有限差分法线),那里是出界区。

### 2. 同一个 seed 必须逐帧复现

- `src/` 下**禁止 `Math.random()`**,`tests/unit/noMathRandom.test.ts` 会扫描拦截。
- 所有随机走注入的 `Rng`(mulberry32),用 `fork()` 派生子流。
- 主循环是定步长累加器,`?test=1` 时**完全不注册 rAF**,只由 `advance(n)` 推进。
- `InputRecorder.record()` 会**就地**把实时输入量化成回放精度。

### 3. 截图回路是这个项目的地基

CI 没有 GPU,WebGL 走 SwiftShader。`npm run shoot` + `tests/visual/smoke.spec.ts`
是 agent **唯一能看见画面**的途径。

**性能预算(实测,1280×720,chase 机位):**

| 配置 | 每帧 |
|---|---|
| 无后处理 | 325 ms |
| 仅 composer(RenderPass + OutputPass) | 347 ms |
| 默认链(bloom + SMAA + 暗角) | 621 ms |

冒烟测试全套 **2~2.5 分钟**(M0 时是 27.7 秒)。**这条回路挂了就等于瞎着写代码,
变得太慢要先停下来解决,不要硬推。**

### 想提速的话,先看这份实测(免得往错的方向使劲)

一次 `driveScene`(goto → ready → 首帧 → advance(120) → 截图)的分解,热态:

| 阶段 | 耗时 |
|---|---|
| JS 加载解析 | ~1.5 s |
| `World` 构造(赛道 + 地形 + 护墙网格) | ~2.1 s |
| 程序化贴图 ×3 | 0.15 s |
| **PMREM 烘焙** | **0.08 s** |
| **首帧渲染(含 shader 编译)** | **~7.4 s** |
| 之后每帧 | 0.62 s |

**三个反直觉的点:**

1. **PMREM 和贴图生成都不是瓶颈**,加起来不到 0.25 秒 —— 别去优化它们。
2. **首帧的 shader 编译才是大头**,但**减少 `goto` 次数省不到这笔钱**:同一个
   `page` 对象的多次 goto 之间,浏览器会复用编译好的 shader。这条路试过了,
   收益在噪声里(把某条测试的 goto 从 6 次减到 3 次,全套时间没有可测的变化)。
3. **冷启动占比很高**:同一段代码第一次跑 12.9 秒,第二次 3.7 秒。CI 每次都是冷的,
   所以本地测出来的时间会系统性偏乐观。

真要提速,剩下的方向是降低渲染分辨率(会动所有截图基准)或砍后处理级数
(会让 agent 看不到真实画面)—— 两个都有代价,**动之前先想清楚代价谁来付**。

## 五、这个项目吃过的亏

按「只有看图才能发现」的程度排序。前四条是历史,**第 5、6 条是 M3 这轮的,
而且是同一类**。

1. **转向左右反了。** 单测断言的是「yaw 与 steer 同号」,而 yaw 正方向到底是左是右
   *正是搞反的那件事* —— 断言和 bug 共用同一个错误前提,83 条测试全绿也拦不住。
   **教训:断言物理位置,不要断言内部约定的符号。**
2. **烘环境贴图时天空整个变黑。** `scene.add(sky)` 会把天空从世界场景摘走。
3. **地形三角形压在赛道上。** 剔除只按重心判断。
4. **贴地阴影不出现。** 扇形三角的绕序反了,整个面朝下被背面剔除。
   护墙现在按左右侧分绕序,`tests/unit/trackMesh.test.ts` 拿三角形**自己的叉乘**
   和着色法线做断言 —— 那条测试验证过:故意改回同一套绕序,它报 -0.9999。
5. **车漆反射成磨砂玻璃。** metalness 高了之后基色只决定反射色调,车身没有自己的
   颜色。**同一个坑踩了两次**:第一次修了 hull,漏了 fin,直到人类看图才发现
   侧翼是块比尾焰还亮的白斑。

### 6. 两次 NaN 黑屏 —— 这一类最难认,务必读完

两次都是 **HDR 值溢出成 Inf/NaN,再被某个模糊/卷积核摊到一大片**:

- **bloom**:天空冲破 `HalfFloatType` 的 65504,高通之后被 mip 链一摊,整屏变黑。
- **天空辐射污染 IBL**:Preetham 在太阳附近能算到上千(shader 里 `EE = 1000`),
  烘 PMREM 时溢出,**整张环境贴图变 NaN,所有 PBR 材质一起变黑**。表现是
  「天空正常、地面纯黑剪影」,看着像地形没被照亮。太阳仰角一过 15 度就触发。

两处钳制现在分别在 `gfx/postprocess.ts` 的 `clampBloomInput()` 和
`gfx/atmosphere.ts` 的 `clampSkyRadiance()`,**都不能删**。

**NaN 有传染性,这是它难认的根源**:把 `bloomStrength` 或 `environmentIntensity`
调成 0 也照样黑,因为 `0 * NaN` 还是 NaN。所以「关掉某个效果看看」这个惯用的
排查手段在这里会给出错误结论。

**而它们差点漏过去的原因,比 bug 本身更值得记住:**

- **`npm run shoot` 的默认 seed 是 42,而 42 恰好是两个 bug 都幸免的少数 seed 之一。**
  所有回归截图都是好的,只有实时模式(默认 seed 1337)是黑的。
  **换 seed 复核,不要只信默认那一张。**
- **既有的冒烟断言结构性地拦不住这类问题。** 「换 seed 会换掉地形与配色」断言的是
  两个 seed 之间平均色差够大 —— 而一张正常图和一张全黑图之间的色差**更大**,
  断言反而更容易通过。方差同理:天空正常而地面归零时,画面对比度更高、方差更大。
  现在补了 `lowerMeanLuminance`(画面下半幅平均亮度),逐个 seed、两头都卡。

### 7. 默认 seed 42 第三次让问题溜过去

「出生点落在逆光位置」这条是人类试玩提的,而**任何一张默认截图都拍不到它**:

| seed | 出生时车头与太阳的夹角 |
|---|---|
| **42**(`npm run shoot` 默认) | **161°** —— 太阳在正后方,完全没问题 |
| **1337**(线上实际默认) | **12.5°** —— 几乎直视太阳 |

和两次 NaN 黑屏是同一个结构:**42 恰好是好的那个**。这已经是第三次了,
所以现在 `World.sunAhead` 把「车头有多正对太阳」暴露成可断言的量,
`tests/unit/trackLayout.test.ts` 拿 12 个 seed × 12 个方位角扫它 ——
不再依赖某个人恰好换了 seed 去看一眼。

### 两个测量方法的坑

- **别拿速度差反推侧向加速度。** 车头转动本身会让机体系下的侧向速度以 ω·v 变化。
  `Vehicle.lateralGripAccel` 直接暴露抓地力实际施加的加速度。
- **测试失败时先找真实原因,别急着放宽容差。** 左右镜像那条差了 0.04°,看着像浮点
  噪声,实际是出生点压平区不够长。放宽容差会把真实原因永久盖掉。
  M3 这轮又遇到一次:空中回正那条从「侧滑角绝对变化 < 5°」改成了「侧滑角**没有向
  0 收敛**」—— 后者才是回正力矩真正的特征,前者的容差会跟着手感数值一起漂。

## 六、当前手感数值(实测)

改 `tuning.ts` 之后这些会变,`tests/unit/vehicle.test.ts` 和 `grip.test.ts` 里的
区间就是它们的规格书 —— **测试挂了不一定是 bug,但一定意味着手感变了,需要人类确认。**

| 项目 | 值 |
|---|---|
| 0 → 100 km/h | **2.3 s**(人类反馈 0.92 s「太快、不写实」后放慢) |
| 极速 | 315 km/h |
| 峰值侧向抓地加速度 | 3.80 g |
| 满舵侧滑角峰值 | 57°(甩尾,不是打转) |
| 赛道长度 | 2.8–3.4 km,10 个 seed 全部可跑完 |

**两条关键设计:**

- **偏航角速度上限由可用侧向力推出(ω = a_lat / v),外加侧滑回正力矩。**
  少了任何一个,车都会一打方向就原地打转。
- **恒定推力下,起步加速度和极速是绑死的。** `a(0) = thrust`,极速由推力与阻力的
  平衡点决定。所以放慢起步必须同步降阻力,否则极速一起掉(实测 thrust 34 → 13
  会让极速掉到 154 km/h)。降的是**线性项**(0.18 → 0.05)—— 那是轮胎滚阻的量级,
  而这台车没有轮胎。代价是松油门滑行更久,那反而更贴合设定。

## 七、后处理链的取舍(有数据支撑,别凭感觉改)

`RenderPass → bloom → OutputPass → SMAA → 暗角`。顺序有硬约束,排错了不报错、
只让画面悄悄变糟 —— 理由写在 `postprocess.ts` 的类注释里。

**AO 实现了但默认不启用**,这是量出来的决定:

| 环节 | 每帧成本 | 画面差异 |
|---|---|---|
| 暗角 | +45 ms | 明显 |
| bloom | +155 ms | 明显 |
| SMAA | +178 ms | 明显 |
| **AO** | +169 ms | **平均 3.8/255,肉眼看不出** |

AO 弱不是配置错了:开阔沙漠、平坦赛道,**而且反重力载具悬浮在地面 1.6 米以上,
连接触点都没有**。半径从 0.45 米加到 2.5 米差异反而更小。M5 的隧道段进来之后,
把 `'ao'` 加回 `DEFAULT_STAGES` 即可。

### bloom 阈值:一个数不能同时服务两个目标

阈值既要**压住整片天空**(否则逆光时全屏发白),又要**放行尾焰**(否则速度感没了)。
上一版为了救逆光把它从 3.5 提到 8,却没同步抬尾焰亮度 —— 尾焰当时是 6.2,正好掉到
阈值以下,辉光整个消失,**是人类试玩才发现的**。

现在两边分开:阈值留在 8 压天空,尾焰亮度(`CRAFT.thrusterFullGain`)抬到约 15。
两处注释互相点名。**改任何一边都要回头核另一边。**

## 八、工作方式

- **分支**:harness 每轮指定固定分支。**PR 合并后必须从 `origin/main` 重开同名分支**,
  不能往已合并的历史上继续堆提交。
- **提交前必过**:`npm run typecheck` / `npm run test -- --run` / `npm run build` /
  `npm run test:visual`。
- **人类的反馈风格**:给的是现象(「车太飘」「视角偏得离谱」「眼睛要瞎掉」),
  需要自己去测量、定位根因。他会验收手感和画面,**这两件事不要自己下结论**。
- **额度有限**,他会喊停。停的时候确保工作已提交推送。

### 常用命令

```bash
npm run dev                                     # 本地开发
npm run shoot                                   # 截图(默认 chase 机位、seed 42)
npm run shoot -- --camera=side --throttle=0     # 静止侧视,看载具本身
npm run shoot -- --seed=99 --frames=420         # 换 seed / 跑到赛道深处
npm run shoot -- --extra=post=none              # 关掉后处理做对比
npm run shoot -- --no-build                     # 复用现有 dist,连拍时省时间
npm run perf                                    # 量每帧渲染成本
```

机位:`chase` / `side` / `front` / `top` / `map`。
`?course=flat` 切回 M1 那块平地,`?post=none` 关掉整条后处理链。

**`npm run perf` 为什么必须存在**:`shoot` 和冒烟测试的墙钟时间**量不出**每帧成本 ——
`Loop.advance(n)` 走 n 个物理步之后只渲染一帧,那两个数字里绝大部分是构建、
启动和场景生成。perf 改成逐帧 `advance(1)`,再用一次截图强制结算 GL 队列。
(顺带一提:页面内的 `performance.now()` 也量不准,它只看到命令提交的时间 ——
实测 0.4 ms/帧,而墙钟是 325 ms/帧。)

## 九、方向转变:反重力 → 真实车辆

**人类已定:载具从「反重力悬浮」改成「真实车辆比赛」。优先级高于 `PLAN.md` 里
剩下的里程碑。**

### 要推翻的

- **`src/game/vehicle.ts` 的整个物理模型。** 现在是单点 raycast 悬浮 + 速度积分,
  没有轮胎、没有悬挂行程、没有档位。
- **`tuning.ts` 的 `VEHICLE` 段几乎全部作废**(thrust、悬浮刚度、偏航包络那些),
  `CRAFT` 段的尾焰也失去意义。
- **`src/gfx/craft.ts` 的载具几何** —— 现在是个没有轮子的悬浮体。人类已经说过
  「车子太假」,新方向下要重做,而且要有轮子。
- **`CLAUDE.md` 里「不用物理引擎、自写 raycast 悬浮」那条技术选型**要重新表述
  (是否引入引擎见下一节的分析)。

### 可以原样留下的(别推倒重来)

- **赛道生成与地面查询**(`trackLayout` / `course` / `spline`)。
  「物理查询的面 == 渲染出来的面」这个不变量对真实车辆**更重要** ——
  四个轮子要各自采样,精度问题会被放大四倍。
- 整条渲染管线:大气、IBL、PBR 贴图、后处理链、护墙。
- 截图验证回路、seeded PRNG、定步长主循环、输入录制。
- `tests/unit` 里除 `vehicle` / `grip` 之外的全部测试。

### 三处「为悬浮而写」但换成真车依然需要的东西

换模型时容易连着一起删掉,那会把踩过的坑重新踩一遍:

1. **偏航角速度上限由可用侧向力推出**(ω = a_lat / v)。真实车辆同样需要,
   否则一打方向就原地打转。
2. **静止时转向权限衰减到 0**。真车也一样,不然是坦克。
3. **悬浮间隙 1.6 米这个前提没了之后,AO 会重新变得有意义**(见第七节 ——
   现在 AO 是默认关的,理由正是「载具悬浮着、没有接触点」)。

## 十、物理引擎:**人类已拍板「加入」**(2026-08-21)

> **决定:引入物理引擎。** 下面这套「建议不引入」的分析是拍板**之前**写的,
> 保留原文是因为它列清了代价 —— 那几条代价现在变成了必须处理的事项,
> 见本节末尾的〈拍板之后要做的事〉。**不要再拿它去反驳已经定下的方向。**

**(以下为原分析)结论先说:建议不引入,把单点悬浮扩展成四轮 raycast。** 理由如下,拍板时可以推翻,
但请先读完再推翻。

### 引擎给什么、不给什么

- **给的**:刚体积分、碰撞检测、约束求解、翻滚姿态。
- **不给的**:**轮胎模型** —— 而赛车手感的绝大部分就在轮胎上。Rapier 没有内置车辆;
  Ammo/Bullet 有 `btRaycastVehicle`,但轮胎是个简化摩擦圆,要写实还是得实现
  Pacejka 之类的公式。

**所以最难的那部分,用不用引擎都要在本项目里实现。** 而引擎能替我们省掉的
(刚体积分 + 地面查询),恰好是这个项目**唯一不缺**的东西。

### 三处具体冲突

1. **确定性 —— 风险最大。** 第四节的不变量 2「同一个 seed 必须逐帧复现」是整个
   测试体系、`?test=1` 步进、以及 M4 幽灵回放的地基。物理引擎的求解器是迭代的、
   对浮点累加顺序敏感;Rapier 声称同平台确定性,跨平台(开发机 vs CI runner)
   不保证。现在这套自写积分是逐位可复现的,而且有测试盯着。
2. **WASM 撞上「零二进制资产」。** Rapier / Jolt 都是编译成 `.wasm` 的,会进 `dist/`。
   `CLAUDE.md` 第一条写的是「仓库里应该只有文本文件」—— 要不要为它破例得人类拍板。
   纯 JS 的 `cannon-es` 不违反这条,但质量与确定性都更差。
3. **包体积。** Rapier3d 的 WASM 一兆起步,当前整个产物才 691 KB,而 M6 是移动端与性能。

### 建议的替代做法:四轮 raycast

`Course.sample()` 已经支持任意点的精确查询,所以把**单点**悬浮扩展成**四个轮子
各自 raycast** 是顺理成章的:

- 每个轮子:悬挂力(弹簧 + 阻尼)+ 轮胎力(纵向驱动/制动、横向侧偏)
- 四个点的力自然产生 **pitch / roll 力矩** → **载荷转移是免费的**,
  刹车点头、过弯侧倾都直接出来
- 车身做刚体积分

**这是绝大多数赛车游戏的实际做法(raycast vehicle),不是妥协方案。**
它保住了确定性、零资产,以及现有的全部测试基础设施。

引擎真正不可替代的场景是**车与车碰撞、翻滚堆叠** —— 而 `CLAUDE.md` 明确
「不做联机 / 多人」,这个需求不存在。

### 如果人类决定还是要用引擎

选 **Rapier**(three 生态最主流、维护最好、确定性最强),并且明确接受三件事:

1. 在 `CLAUDE.md` 里为 WASM 破例,写清楚理由
2. **放弃跨平台逐帧复现**,M4 的幽灵回放改成存**位置轨迹**而不是存输入重放
3. 首屏体积涨 1MB+,留到 M6 处理

### 拍板之后实测:上面那条「确定性风险最大」是**错的**

原分析把「确定性」列为最大风险(第 1 条),理由是求解器迭代、对浮点累加顺序敏感。
**接上之后量了一遍,这条对 WASM 编译的引擎不成立。**

WebAssembly 的浮点语义由规范强制(IEEE-754,不允许 FMA 合并、不允许重结合、
没有扩展精度),所以同一份 wasm 在任何符合规范的运行时上结果必然一致 ——
这恰恰是**原生**编译的物理引擎做不到的事。原分析拿的是原生物理引擎的常识,
套到 wasm 上就不对了。

实测:接触密集的场景(倾斜地面 + 持续偏心力 + 一路滑移翻滚)跑 600 步,
**Node 和 Chromium 的 10 个状态字段逐位完全相同**。
守卫在 `tests/unit/physics.test.ts`,并钉了一组基准值。

于是原分析里那两条连带的让步也不需要了:

- 车辆物理单测**继续留在 vitest**(8 秒),不用搬进 Playwright(2 分钟)。
- M4 幽灵回放**可以继续存输入序列**重放,不必退化成存位置轨迹。

**基准值那条测试哪天红了,不要放宽它。** 它红只有一个含义:求解器动过了
(多半是升级了 Rapier),所有手感数值和回放基准都要重新核,需要人类确认。

### 为什么用 compat 版(体积更大却选了它)

| 包 | JS(gzip) | wasm(gzip) | 合计 |
|---|---|---|---|
| 无引擎(改之前) | 202 KB | — | **202 KB** |
| `rapier3d`(独立 .wasm) | 235 KB | 762 KB | **997 KB** |
| `rapier3d-compat`(base64 内联) | 1285 KB | — | **1285 KB** |

独立 wasm 版小 288 KB,但**它在 vitest(Node)里根本 import 不起来**:那个包
是给打包器用的,`package.json` 没有 `main`/`exports` 入口;加 alias 绕过之后,
wasm-bindgen 的堆表又会在 Vite 的 Node 变换下失配(`getObject` 返回 undefined)。

而「浏览器用一个包、测试用另一个包」是不能接受的 —— 这个项目整套测试的前提
就是**单测能预测运行时行为**,两个不同的构建产物会把这个前提悄悄挖空,
而且是那种「测试全绿但线上是坏的」的挖法,这个项目已经栽过两次。
**用 288 KB 换「测的和跑的是同一个二进制」。**

### 拍板之后要做的事(人类已选择引入,这几条从「代价」变成「待办」)

1. **在 `CLAUDE.md` 里为 WASM 破例。** 「零二进制资产」是宪法第一条,
   引擎的 `.wasm` 会进 `dist/`。要写清楚破例的范围(只限物理引擎运行时,
   贴图/音效/模型仍然一律程序化生成)和理由。
2. ~~**确定性的地基要重铺。**~~ **不需要了,见上面那节的实测。**
3. **首屏体积 202 KB → 1285 KB(gzip)**,留到 M6。
4. **轮胎模型仍然要自己写。** 引擎不给这个,而赛车手感的绝大部分在这儿。
   这一条不因为拍板而改变。

### 关于人类的工作量(容易被误解,写清楚)

上面说的「自己写」指的是**本项目代码里要有这部分实现,由接手的 AI 来写**,
不是要人类手写代码。人类的角色不变:**试玩、给现象级反馈**(「车太飘」
「起步太猛」),AI 负责测量、定位根因、修改。

唯一真实增加的成本是**调参循环变长** —— 轮胎参数比悬浮更多、更敏感,
大概率需要多几轮「试玩 → 反馈 → 调整」。

## 十一、两条视觉反馈(已做,等人类看图)

1. **逆光再收一档。** 曝光 `0.42 → 0.38`、bloom 强度 `0.12 → 0.09`。
   正对太阳那一帧(`sunAhead = 1.00`)全幅平均亮度 137.8 → 126.1,
   上半幅 192.1 → 185.8:眩光收进太阳周围,地平线和沙丘的形状重新读得出来。
   **代价量过了**:尾焰辉光暗了约四分之一(没有消失)。原因和唯一还没试过的
   补救方向写在 `tuning.ts` 的 `bloomStrength` 注释里。
2. **出生点避开逆光。** 做法是**只换起点,不动曝光**:赛道是闭环,每个采样都是
   合法起点,`arc` 又只是 `下标 × 间距`,所以换起点 = 数组循环移位 + 重编 arc,
   **赛道几何一个顶点都没动**,第四节不变量 1 不受影响。选点是最小干预 ——
   原来的 0 号点不逆光就原样保留,24 个 seed 里只动了 7 个。
   避让半角 `TRACK.startSunAvoidance = 70°` 由相机水平半视角倒推,不是拍脑袋。

新增的两个调试开关:`?exposure=` / `?bloom=`,和 `?post=` / `?course=` 一类。
逆光这事已经被打回三次,原来每次 A/B 都要重新 build 才能跟上一版比。
**定稿值仍然只住在 `tuning.ts` 里**,URL 参数不参与部署、不进任何基准。
